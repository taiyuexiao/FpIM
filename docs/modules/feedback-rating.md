# 模块：评价与反馈（一期）

> 状态：🚧 后端+基础 UI 已通（评价/反馈接口实测通过）　｜　最近更新：2026-10-04

## 摘要

问题解决后的**评价（评分 + 评语）** 与产品**意见反馈**通道。评价数据进画像/统计（"被认可"是反刷量铁律的下游动作背书之一）；意见反馈是员工吐槽产品的入口，与业务问题闭环分离。

## 动机

领导要求"用户可以进行评价、反馈"：
1. 问题闭环缺"提问方满意吗"这最后一环——解决件数之外需要**解决质量**信号；
2. 帮助榜/画像的进榜指标需要"被确认有效"背书（PRD 反刷量铁律），评价就是背书来源；
3. 员工对平台本身的意见要有出口，避免与业务问题混在一起污染 issue 数据。

## 范围与非范围

- 范围内：解决确认后的评价入口（星级/标签 + 评语）；已解决问题的补评价；评价展示（责任人可见）；产品意见反馈入口（表单）+ 后台查看列表。
- 明确不做：评价申诉/仲裁、差评自动触发流程、匿名评价（默认实名，走留痕价值观）、对外评价 API。

## 上下游依赖

- 上游：issue 状态机（`resolved` 后才可评价，见 issue-loop.md）；用户会话（issue_loop 的 resolve_confirm 流）。
- 下游：统计（评价计入帮助榜/画像的"被认可"口径，stats-board.md / directory-profile.md 口径同步）。

## 关键接口与运行时信息

| 接口 | 说明 |
|---|---|
| `POST /api/v1/issues/{id}/review` | 提问方对已解决问题提交评价（rating 1-5 + tags + comment）；一问题一评价，可改 |
| `GET /api/v1/issues/{id}/review` | 读评价（参与者可见） |
| `POST /api/v1/feedback` | 产品意见反馈（category + content） |
| `GET /api/v1/admin/feedback` | 意见反馈列表（管理员） |

- 存储：`issue_reviews`（issue_id 唯一，评分/标签/评语/时间）+ `product_feedback`（或复用既有 feedback 表，实现时核对 `services/feedback` 现状再定）。
- 前端：解决确认弹窗后追加评价步进；问题详情侧栏显示评价；「设置」或 rail 底部放「意见反馈」入口。

## 设计决策与假设

- **只让提问方评价**：与 BR-02（仅提问方确认解决）同一逻辑——被服务的人说了算。
- **评价在解决后开放，且不催评**：不弹窗打扰；已解决的问题卡上留入口，7 天内可补评。
- **差评不公开、不进负向榜**：沿用 D3 红线；差评只进责任人可见的详情与管理员聚合。
- **评价标签预设**（如"解决及时/讲解清晰/态度好"）+ 自由评语，降低评价成本。

## 0. 先说结论

附件文档的核心判断对我们是**利好**：它把「原人际私聊自动代理（R2）」列为第三方 IM 的平台阻塞（"若只开放机器人单聊……R2 尚未实现，不能计入完成率"），而 **FpIM 是自建 IM——消息协议、已读游标、发送身份、人工接管全部自有**，R2 没有平台阻塞，是全功能可行的。这正是「基于首问内核自研 IM」这条路线在二期的复利。

我们的既有资产对得上附件架构的多个模块：

| 附件模块 | FpIM 现成对应 |
|---|---|
| IM Adapter / 事件归一化 | `im_gateway`（WS 帧）+ `im.messages` 同库留痕 |
| Conversation Control（人机控制/任务归属） | 一期「清空/删除 per-user」「会话偏好」模式可延用；`control_epoch` 需新建 |
| Policy Service（介入/委托/授权） | `group-agent` 的触发判定 + 动作确认（雏形） |
| Knowledge / Retrieval | `faqs`/`contents` + agent-service RAG（512/1536 双向量空间） |
| Tool Broker | `group-agent` 的 ActionExecutor（动作确认后才写业务，正是雏形） |
| Delivery / 发送凭据 | `im.messages` seq/ack + 已读回执（一期已做） |
| 审计 | `audit_logs` 已接线（platform-hardening） |

## 3. 与附件架构的裁剪建议（我们不必全抄）

1. **事件层**：附件的"归一化 IM 事件"对我们就是 `im.messages` 触发器式的桥（`group-agent/integration.py` 已是这个形态）——不引入独立事件总线，二期继续同库直调。
2. **控制权/接管**：附件 `control_epoch` 的 CAS 语义值得照抄（发送携带 epoch 拒旧），但我们发消息与接管同进程同库，可以做得比第三方更强（"接管生效后旧 Agent 消息绝不发出"是可实现的强保证）。
3. **能力声明**（附件 §13.2 capabilities 矩阵）：用于外部 IM 接入（group-agent 的外部 HTTP API）应照做；自建 IM 内部不需要。
4. **预算与幂等**：附件 §9.2/§11.4（工具步数预算、幂等键、outbox）在工具网关落地时必须带上——我们已有 `clientMsgId` 幂等传统。
5. **验收用例**（附件 §16 K/D/F/X 四组）：直接改编为我们二期的测试清单（把"第三方租户"换成"自建 IM+飞书适配器"）。

## 4. 风险与红线（对齐我们的不可协商约束）

- **agent 只读只推理只产草稿** → 二期引入"受控执行"不等于放开写权限：一切写（发消息/建问题/写业务）经 Tool Broker + 动作确认（`group-agent` 的 ActionExecutor 模式推广）。
- **消息与问题同库同事务** → 模板/记忆/委托策略表同库（public schema 新表，DDL 进 agent-service/scripts/ddl/ 约定）。
- **留痕铁律** → Agent 代发消息带自动化标识、可审计（审计进 `audit_logs`）；模板使用记录留痕。
- 披露控制红线（附件 §8.1）：跨会话检索结果分享给当前受众前必须过"可分享"检查——**不得先给模型再让模型决定泄露与否**。

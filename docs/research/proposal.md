# FpIM 重构方案建议

## 一、需求理解

### 业务本质

这次重构不是"加一个聊天功能"，而是**把平台的闭环从"找到人"延长到"解决问题并留下证据"**。

现状链路：提问 → AI 找人 → **断点（线下邮件沟通，过程丢失）** → 无从考核。

目标链路：提问 → AI 找人 → 一键进会话 → **沟通全程留痕** → 问题标记解决/未解决 → 沉淀进报表 → 服务人才选拔。

领导说的"管理理念"翻译过来是三条产品原则：

1. **制造麻烦倒逼解决**：问题一旦被问出就进入留痕状态（未联系/处理中/已解决），超时不解决会被看见、被催办、被计入部门统计——被询问者不能装死
2. **过程即数据**：每一次问答、每一段处理对话都是考核素材，谁问得多、谁答得好、哪个部门被问得最多，全部可量化
3. **画像进 HR 链路**：个人主页上的标签、画像、被问解决率，与人力资源系统联动，纳入人才选拔

### 功能拆解

| 模块 | 内容 | 与现有系统的关系 |
|---|---|---|
| IM 核心 | 单聊（先行）、已读回执、历史漫游、离线消息、文件/图片 | 全新 |
| 通讯录 | 组织树浏览、点人进会话、免加好友 | 现有名片库改造 |
| 个人主页 | 合并现有个人中心/标签/自画像/他画像/部门职责/上级标注，主页间可互跳 | 现有 /mine、/profile/:id 合并重构 |
| 搜人入口 | 保留 ChatGPT 式左侧会话列表 + 右侧提问框；AI 名片上"发消息"按钮直接建会话 | 现有 /ask 保留并加跳转 |
| 问题闭环 | 会话可关联问题，状态机（未联系/处理中/已解决/未解决）、留痕、知识沉淀 | ✅ **已实现，本次是"换渠道"而非"从零新建"**（见下方勘误）——`issues` 五表、事件时间线、邮件往来、沉淀候选、FAQ 全部已存在 |
| 统计报表 | 提问量排行、提问价值（反馈+解决率）、部门被问排行、解决成果、生成报告发领导 | 新建，数据源 = IM 消息 + 已有 issues/issue_events + 反馈 |
| HR 联动 | 画像/排名数据对接人力资源系统 | 后期，预留接口 |

## 二、IM 内核选型建议

两个推荐方案，按团队偏好二选一：

### 方案 A：FastAPI 自研 WebSocket IM（推荐）

**理由**：本项目的差异化价值全部在聊天之外（问题状态机、催办、报表、AI 搜人、HR 联动），这些恰恰是任何现成 IM 都给不了的；而 208 人、单聊为主的规模下，自研 IM 的技术风险可控（单实例 uvicorn 承载 ≤100 并发长连接绰绰有余）。换来的是：

- 消息落自己的 PG，报表统计零 ETL
- 自定义消息类型（问题卡/解决确认/催办提醒）与问题闭环原生一体
- 账号、组织树、AI 搜人链路零对接层
- 不引入新语言栈、新中间件，运维面不变

**代价**：4~8 人周开发 + 消息可靠性（ACK/重发/幂等/断线重连）要自己趟一遍。

### 方案 B：JuggleIM 内核 + Vue3 自研 UI

**理由**：Apache-2.0 干净协议、活跃维护、"IM 内核 + 自有业务后端"模型——FastAPI 调 Server API 注册用户签 token，前端 Web SDK 直连，消息可靠性由内核兜底。适合想快速上线、不愿碰消息可靠性细节的情况。

**代价**：多一套 Go 组件 + MySQL；报表数据需走 Webhook 回流 PG；自定义业务消息要绕一层。

### 不推荐的方案及原因

OpenIM（客户端 AGPL + 6 组件过重）、野火（CC BY-ND + PC 付费墙 3.9 万起）、Mattermost（250 人上限）、Rocket.Chat（已读回执付费 + Mongo 割裂）、Zulip（部署最重 + 无嵌入）、Tailchat（React）。详见各调研文档。

## 三、方案 A 技术设计要点

### 架构

```
浏览器 Vue3 ──WebSocket──> backend (FastAPI, 新增 /ws 网关)
                              ├─ 消息服务：conversations / messages / read_cursors 三表落 PG
                              ├─ 在线状态：内存连接注册表（多实例时 Redis pub/sub）
                              └─ 业务钩子：消息事件 → 问题状态机 / 报表统计
现有 agent-service :8100 不动，继续负责搜人问答
```

### 数据模型（新增，public schema）

- `conversations`：会话（单聊 type=direct，成员两人；预留群聊 type=group）
- `conversation_members`：成员、未读数、置顶/免打扰
- `messages`：消息体（msg_type：text/image/file/**issue_card**/**resolve_confirm**/**urge**）、发送者、时间、状态
- `message_receipts` 或游标式 `last_read_message_id`：已读回执
- `issues` 增加 `conversation_id` 关联：问题与会话绑定，处理过程天然留痕

### 关键交互链路

1. **搜人 → 进聊天**：AI 名片加"发消息"按钮 → 调 `POST /conversations`（幂等：两人已有单聊会话直接复用）→ 前端跳转会话页
2. **问问题即立项**：从搜人入口跳入的会话自动携带问题上下文（issue_card 消息），进入"待响应"状态；被问方回复开始计时为"处理中"；提问方点"已解决"闭环，超 24h 未响应自动催办（这就是"制造麻烦"的落点）
3. **个人主页**：合并 /mine 与 /profile/:id 为一个 Profile 页（看自己时带编辑入口，看别人时带"发消息"按钮）；上级、部门路径可点击互跳（飞书式）
4. **通讯录**：现有名片库页改造为通讯录（组织树 + 搜索 + 点人进会话/看主页）

### 报表与 HR 联动

- 数据源：messages（提问/响应量、响应时长）+ issues（解决率、解决时长）+ feedback_events（提问价值评价）+ 现有 agent 推荐日志
- 指标：提问量排行（按人去重）、被问量部门排行、解决率/平均解决时长、提问价值分（有帮助反馈率 × 解决率加权）
- 报告：模板化生成（周/月报），HTML 页面 + 导出 PDF + 定时发领导。✅ **可直接改造复用**：`backend/app/api/v1/mail.py` 已有 SMTP 中继投递与 AI 拟稿能力；IM 上线后改用「小管家」会话推送为主通道
- HR 联动：对外提供只读 API（人员画像 + 被问解决指标），由 HR 系统拉取

## 四、分期建议

| 期 | 内容 | 出口标准 |
|---|---|---|
| P0 | 单聊 MVP：会话/消息/已读/离线拉取/通讯录直聊 | 两人互发消息、刷新不丢、已读正确 |
| P1 | 搜人→进聊天打通；个人主页合并；issue_card 自定义消息 + 问题状态机 + 催办 | 完整跑通"提问→沟通→解决→留痕"闭环 |
| P2 | 统计报表 + 报告生成 + 邮件发送 | 领导收到第一份自动周报 |
| P3 | 群聊、文件/图片增强、HR 系统对接 | 按实际需要排期 |

## 五、决策点（需要领导/团队拍板）

1. IM 内核：自研（A）还是 JuggleIM（B）——核心权衡是"4~8 人周投入" vs "引入 Go 组件 + 消息不在自己库"
2. 问题状态机的严格程度：是否需要"超时未解决自动升级给上级"（制造麻烦的力度）
3. 群聊是否首期就要（建议不要，单聊先跑通闭环）
4. 移动端是否规划（本期明确 PC 优先，结构上预留）
5. HR 联动的对接方式（我们推 API 还是 HR 系统来定契约）

| 原文表述 | 核对结果（以本机工作副本为准） |

**缺失原因**：这些文件在本机 git 里全部处于**未跟踪（`??`）状态**，`07_issues_knowledge.sql` 也不在 GitHub 的 DDL 目录里（GitHub 只有 `01`~`06`）。所以只看公开仓库会得出完全相反的结论。

**已存在的完整链路**（这就是领导说的"邮件往来太低效"的那个东西）：

```
问答记录 → LLM 判定有效问题 → 同步为 issue（去重/记重复次数）
        → 指定责任人 assignee_person_id
        → 邮件沟通（AI 拟稿 → SMTP 发出 → 收回信 → LLM 分析）
        → 全程写入 issue_events 时间线
        → 标记已解决（自动生成知识沉淀候选）
        → 管理员确认 → FAQ / 知识文章
        → 问答时优先命中 FAQ
```

配套设计与页面也都已有：`docs/问题闭环与知识库设计.md`（七章设计稿）、前端 `src/stores/issues.js`、`src/services/api/issues.js`、`src/components/ask/MailDialog.vue`、`src/views/MineView.vue`、`src/views/KnowledgeView.vue`（**路由已注册，侧边栏被注释隐藏**——与"前端被隐藏"完全吻合）。

**对排期的实质影响（重要）**：

1. **问题闭环不是新建，是"换渠道"**——把 `mail_messages` 这条沟通链路，替换/扩展为 IM 会话消息。问题、事件时间线、责任人、解决标记、知识沉淀**全都不用重做**。
2. 我此前方案里"问题闭环 = 完整新建模块"的估算**严重高估**，应按"渠道替换 + 状态机扩展"重新评估。
3. 原设计文档把"工单办理、转办、催办升级"列为延后功能仍然成立——但基础设施（表、事件流、沉淀链路）已经打好，不是白地起楼。

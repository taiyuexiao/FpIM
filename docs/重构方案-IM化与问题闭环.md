### 1.2 现状断点（有代码级证据）

原设计链路（`核心业务流程设计.md` 链路一）第 6 步：「用户在人员主页查看联系方式……并通过联系方式联系负责人」← **断点就在这里**。

`public.people.contact` 之后就是线下邮件。全库检索证实：仓库里**没有任何**"邮件 / 工单 / 催办 / 已解决"的实现（`邮件` 0 命中）。

> 现状 = **AI 把人找对了，然后信息掉进黑洞。**

### 1.3 领导"管理理念"的产品化翻译

| 领导原话 | 产品机制（v3 定稿） | 落地物 |
|---|---|---|
| 制造麻烦逼被询问者解决 | 问题一问出即进入**留痕**状态；被问方**一读就摘不掉**（已读是硬证据），处理过程全程在案 | `issues` 状态机 + **已读/未读游标** + `issue_events` |
| 过程即数据 | 每段沟通、每次转办、每个解决结论都是考核素材 | `im.messages` + `issue_events` |
| 画像/排名服务人才选拔 | 个人主页挂"被问/解决/知识贡献"指标，全员公开可见 | 个人主页扩展 + 报表看板 |

> ⚠️ v3 调整：原"超时自动升级"已按 D2/D8 移除。**倒逼力由"系统自动追责"改为"读取即留痕"**——设计上更轻，但要求前端必须把"已读"这件事做得非常显眼（见 §3.6）。

### 1.4 【关键设计原则】"部门被问最多"不是排行榜，是"职责模糊地图"

- 若"被问最多"被解读为**负面** → 部门开始互相推诿、能把问题挡在门外就挡 → **直接违背"制造麻烦逼解决"的初衷**。
- 若被解读为**正面** → 诱发刷存在感、抢简单问题。

**正确定位**：被问量是"**该事项缺自助知识 / 责任人不清 / 流程不顺**"的**信号**。领导真正要看的不是"谁被问得多"，而是"**哪些高频问题应该沉淀成知识，让下次不用再问人**"。

### 3.3 IM 内核：自研的完整技术决定（D1）

**为什么自研（三条，第 2 条是决定性的）：**

1. **规模无风险**：208 人、峰值并发 ≤100 长连接，单实例 uvicorn 足够；多实例加 Redis pub/sub。这个规模上 Kafka/Mongo 是**负资产**。
2. **数据必须在自己库里**（决定性）：下半场的全部价值是**报表、问题状态、人才画像**，全是 SQL 聚合。若消息在 MySQL/Mongo（JuggleIM/野火/OpenIM 都是），就要维护一条**同步管道**，必然产生"报表数字 ≠ 聊天记录"的经典事故。自研 = 消息与 issue **同库同事务**，报告数字恒等于聊天记录。
   → **D6（小管家在 IM 内推报表）这条需求，只有在消息与报表同库时才干净。这是 D1 选自研最强的理由。**
3. **自定义消息类型与状态机同源**：`issue_card` / `resolve_confirm` / `handoff` / `report_card` 本质是状态机事件的投影。自研可以"事件落库 → 同时投射成消息"，一步到位，不用绕 webhook。

**具体技术栈：**

- **传输**：FastAPI `WebSocket`（`uvicorn[standard]` 已含 `websockets`，现有 requirements 里就有）；**消息用 JSON 文本帧**，不自造二进制协议（208 人不需要，可读性和排障效率更重要）
- **协议**：WS 负责实时收发与推送；历史拉取、文件上传、报表查询走 REST（HTTP 可缓存、可重试、好调试）
- **连接管理**：进程内连接注册表（`person_id → {conn}`）；预留 Redis pub/sub 接口以便多实例
- **桌面壳**：Electron 主进程负责全局截图快捷键、系统通知、开机自启、托盘；渲染进程直接加载现有 Vue3 站点

**诚实的代价**：IM 长尾在**消息可靠性**——ACK/重发/幂等/离线拉取/断线重连/多端同步。**必须在写代码前先定死协议**（§3.5），否则后期返工。工作量估算见 §5。

### 3.4 数据模型

#### ⚠️ 命名冲突（Kimi 方案未提）

`public.sessions` / `public.messages` **已被 AI 问答占用**（backend `/api/v1/sessions`、`/api/agui/*`）。IM 表**绝不能再叫 sessions / messages**。

→ **新建独立 schema `im`**（与 `public` / `agent` / `rag` 并列）。

```sql
-- ============ 会话（单聊 + 群聊，D7）============
im.conversations
  id                bigserial pk
  type              text      -- 'direct' | 'group'
  direct_key        text      -- 单聊: 两人 id 排序拼接, UNIQUE → 会话幂等复用
  name              text      -- 群名（单聊为 NULL）
  avatar            text      -- 群头像
  owner_id          text      -- 群主（单聊为 NULL）
  member_count      int       -- 冗余, 便于列表渲染
  last_message_id   bigint
  last_message_at   timestamptz
  created_by        text
  created_at        timestamptz

-- ============ 会话成员 ============
im.conversation_members
  conversation_id      bigint
  person_id            text     -- → public.people.id
  role                 text     -- 'owner' | 'member'      (群聊用)
  last_read_message_id bigint   -- ★游标式已读, 不逐条写回执
  unread_count         int
  pinned               bool     -- 置顶
  muted                bool     -- 免打扰
  joined_at            timestamptz
  pk (conversation_id, person_id)

-- ============ 消息 ============
im.messages
  id                bigserial pk  -- ★全局单调递增 = 增量拉取唯一游标
  conversation_id   bigint
  sender_id         text
  msg_type          text  -- text|image|file|audio|video|system
                          -- |issue_card|resolve_confirm|handoff
                          -- |ai_summary|report_card
                          -- v3 移除 urge（无超时机制）
  body              text
  payload           jsonb -- 卡片/富内容
  client_msg_id     text  -- ★幂等: UNIQUE(sender_id, client_msg_id)
  reply_to_id       bigint
  mentions          text[] -- 群聊 @
  status            text   -- normal | revoked
  created_at        timestamptz
  index (conversation_id, id)

-- ============ 附件（本地磁盘内容寻址，D5）============
im.attachments
  id, message_id, filename, ext, size, mime,
  storage_key, sha256, width, height, duration_ms, created_at
```

#### ⚠️ issue 与 conversation 是 M:N（修正 Kimi 的 1:N）

Kimi 设计是 `issues.conversation_id`（1 issue 绑 1 会话）。但真实业务是：一个会话会聊出**多个**问题；一个问题**转办**后会出现在**新**会话（甚至新建的问题群）里。

→ 用"**锚点 + 当前**双指针"落地：

```sql
-- ============ 问题（放 public 业务事实层）============
public.issues
  id                     bigserial pk
  title                  text
  body                   text
  asker_id               text   -- 提问人
  current_owner_id       text   -- ★当前责任人（转办会变；群聊问题必须指定唯一责任人）
  owner_department_id    int    -- 归属部门（部门维度统计）

  -- 来源追溯（把 AI 推荐依据串进来）
  source_type            text   -- 'agent' | 'manual'
  source_conversation_id bigint -- ★主会话（单聊或问题群）
  source_message_id      bigint -- ★锚点消息 = 问题卡所在位置
  source_agent_trace_id  text   -- ★关联 agent.agent_traces, 推荐依据可回溯
  concept_id             bigint -- ★关联 agent.concepts, 复用现有概念体系

  status                 text   -- draft|open|in_progress|resolved|unresolved|cancelled
  priority               text

  -- 留痕时间戳（全部由事件推导，不手写）
  created_at             timestamptz -- 提问时刻
  first_read_at          timestamptz -- ★被问方首次已读 → "他看到了"的铁证（v3 新增）
  first_response_at      timestamptz -- ★被问方首次回复 → "他接了"的铁证
  resolved_at            timestamptz
  resolution_summary     text        -- 解决结论（知识沉淀素材）
  updated_at
  -- v3 移除（D2/D8）：response_due_at / resolve_due_at / urge_count / escalation_level

-- ============ 问题事件（唯一事实源 · 轻量事件溯源）============
public.issue_events
  id, issue_id, event_type, actor_id,
  from_owner_id, to_owner_id, payload jsonb, created_at
  -- event_type: created | assigned | ★read | responded | accepted | handoff
  --           | resolved | reopened | unresolved | cancelled | knowledged | rated
  -- ★read = 被问方首次读取问题卡（每个 issue 只记一次，保证 first_read_at 可审计）
```

**为什么 `issue_events` 必须是唯一事实源**：所有报表指标（首次已读时长、首次回复时长、解决率、转办链、知识沉淀数）都从事件表聚合，`issues` 表只是**投影**。好处：① 报表口径**可追溯到具体事件**（满足 v4 §十二 既有硬要求）② 不会"状态改了但历史丢了" ③ 后续口径变更可以**重算历史**。

#### 状态机（最小集 · v3 已去时限）

```
draft（AI 已给责任人候选，待提问方确认）
  └→ open（已指定责任人；被问方未读）
       ├─[被问方首次打开问题卡]→ 记 read 事件 + first_read_at   ★"他看到了"
       ├→ in_progress（被问方首次回复）[记 first_response_at]    ★"他接了"
       │    ├→ resolved    （★提问方确认已解决）[记 resolved_at]
       │    ├→ unresolved  （解决不了 / 双方放弃，须填原因）→ 可 reopen
       │    └→ handoff     （横向转办，owner 变更，回 open，不重算任何时限）
       └→ cancelled（提问方主动撤销）
```

**两条关键约定**：
1. **`resolved` 只能由提问方确认**，被问方不能自评。否则会出现"被问方为了好看自己点已解决"——这是没有超时机制后最容易出的漏洞。
2. **`read` 事件每个 issue 只记第一次**。语义是"他看到了"，不是"他在跟进"——避免被解读成考勤式监控。

#### ⚠️ 群聊里"问题归谁"——必须定的一条

群聊进了首期（D7），就绕不开这个问题：**一个问题在群里问的，责任人是谁？**

两个选项：

| 选项 | 后果 |
|---|---|
| ❌ 问题归"群"（无个人责任人） | 报表里个人不背责任 → **集体负责 = 无人负责**，闭环落空，违背整个项目的初衷 |
| ✅ **立项时必须从群成员中指定唯一责任人**（默认群主） | 责任明确，报表可算；群聊只是"沟通场所"，责任仍在人身上 |

→ **强烈建议后者。** 群聊解决的是"多方会诊"的效率，不解决"谁负责"；责任必须落到个人，否则这套系统的考核基础就塌了。

### 3.5 【必做】IM 协议六件套（写代码前必须定死）

| 问题 | 方案 |
|---|---|
| **消息顺序** | 服务端 `im.messages.id`（bigserial）作为**会话内单调游标**；客户端按此排序，**不用时间戳**（客户端时间不可信） |
| **幂等** | 客户端生成 `client_msg_id`（uuid）；`UNIQUE(sender_id, client_msg_id)`；重发不产生重复 |
| **投递确认** | 服务端落库即回 `ack(client_msg_id → server_id)`；客户端未收到 ack 才重发（可无限重试，幂等兜底） |
| **离线 / 漫游** | 重连后按 `last_synced_id` **增量拉取**；**不做"离线消息队列"**（消息永久在库，天然漫游） |
| **已读 / 未读** | **游标式**：`conversation_members.last_read_message_id` + `unread_count`，**不做逐条回执**。★ 这是 D2 的**核心载体**：进入会话即写回游标 → 红点清零；同时把"问题卡被首次读取"抽取为 `issue_events.read`（§3.4）。**一套机制同时满足「未读红点」和「已读留痕」两个需求**，不用做两套 |
| **群聊扇出** | 单群上限 **100 人**（D7）；发消息时按成员数批量 `UPDATE unread_count`（100 人无压力，不做异步队列） |
| **多实例** | 单实例先跑；扩容时加 Redis pub/sub 广播，`im.messages.id` 仍是唯一顺序源 |

### 3.6 责任留痕：已读 / 未读（D2 定稿 · v3 取代原"催办"设计）

> **决策**：不做超时、不做延期审批、不做升级通知。**留痕机制 = 已读 / 未读。**
> 倒逼力来源从"系统自动追责"改为"**读取即留痕，不可撤销**"。

#### 一套机制，两个需求

已读/未读在 IM 里是**基础交互功能**（未读红点），在我们这里同时是**责任证据**——这是这个决策最划算的地方：

| 用途 | 实现 |
|---|---|
| 未读红点 / 未读计数 | `im.conversation_members.unread_count`（会话级，会被覆盖，用于 UI） |
| 「他看到了」的不可撤销证据 | `issue_events(read)` + `issues.first_read_at`（问题级，只记第一次，永不覆盖） |

⚠️ **两者必须分开存**：会话游标是"当前读到哪"，会被后续阅读不断覆盖；而 issue 关心的是"**这件事他第一次是什么时候看到的**"。用游标当证据 = 证据会被冲掉。

#### 规则（四条）

1. **只认责任人的已读**。群聊里其他人读过不算数——否则"群里 20 个人都看了"会掩盖"责任人没看"。责任人 = `issues.current_owner_id`；转办后，**新责任人的首次已读**另记一条 `read` 事件。
2. **进入会话看到问题卡即写回已读**（前端在卡片进入视口时上报一次，不做滚动监听）。写回的是"已读游标"，服务端据 `current_owner_id` 判断要不要同时落 `issue_events.read`。
3. **未被读取 = 未读状态持续存在**，不做任何自动提醒。它的价值是**反向保护**：如果责任人确实不知道这事，`read` 事件缺失**恰好替他说话**——这是这套机制能同时被提问方和被问方接受的原因。
4. **不做逐条消息回执**（208 人规模下是纯浪费）。只做会话游标 + 问题级首次已读。

#### 呈现要求（这条不满足，机制就等于没做）

前端必须把"已读"做得**显眼且不可回避**：

- 问题卡上直接显示状态徽标：**`未读` / `已读 3 小时后回复` / `已读，未回复`**
- 提问方列表里可筛"**对方已读但我还没得到回复**"——这正是提问方最想要的那个视图
- 被问方的"我的待办"里，问题卡置于最上方且**未读态高亮**
- ❌ 不展示"已读后停留了多久""读了没回的天数排行"——一旦这么做，就退化成考勤监控，会引发"干脆不点开"的对抗行为（这正是砍掉超时机制后要避免的）

#### 报表口径的变化

原"响应时限达标率"（有红线的**合规**指标）→ 改为**无红线的分布指标**：

| 指标 | 口径 | 用途 |
|---|---|---|
| 首次已读时长 | `first_read_at - created_at` 的分布（中位数 / 90 分位） | 看整体响应氛围 |
| 首次回复时长 | `first_response_at - first_read_at` 的分布 | 看"读了之后的行动力" |
| 已读未回复率 | 有 `read` 无 `responded` 的比例 | **这是新的核心风险指标** |

> **为什么改成分位数而不是达标率**：没有约定时限，就不该有"达标"这个概念。给领导看的是**趋势和异常**，不是合格线。

#### 如日后要恢复超时机制（成本很低，不用现在做）

数据基础仍在：`public.responsibility_assignments` 已存有 `time_limit` / `transfer_condition` / `escalation_path`，`public.people.manager_id` 已有。真要启用，**只需加一个调度器 + 两个 due 字段**，schema 不用重构——因为 `first_read_at` / `first_response_at` 这两个关键时间戳从现在起就已经在积累了。**这是把这个机制砍掉却依然安全的原因。**

### 3.7 AI 的三个新位置（现有主链完全不动，只加出口）

1. **入场（复用现有能力）**：AI 搜人 → 产出 `issue draft`（责任人候选 + 可解释依据 + `agent_trace_id`）。点"确认并联系" = 立项 + 建会话（或拉问题群）+ 发 `issue_card`。
2. **场中（新增）**：issue 关闭时，AI 生成 `ai_summary` 摘要消息 + **"建议沉淀为知识"** 标记 → 这是"首问责任 → 首问知识化"正循环的入口。
3. **横向（新增）**：被问方点"这不是我负责的" → **转办**，AI 复用 `people_ranker` 推荐转办对象。

**必须继承的既有约束（写进开发规范）**：
- ❌ AI **不得**直接修改 `issues.status`、**不得**主动发消息 —— 只产草稿/建议（继承"agent-service 只读、只推理、只产草稿"）
- ❌ 两个向量空间（Concept 512 维 / RAG 1536 维）**继续隔离**
- ✅ **分层降级继续保留**：AI 挂了，IM 与 issue 闭环必须照常工作

### 3.8 报表与人才选拔

**数据源**：`im.messages`（沟通量）+ `public.issue_events`（生命周期）+ `public.feedback` / `agent.feedback_events`（评价）+ `agent.agent_traces`（推荐质量）

**复用现成框架**：`public.statistics_definitions`（`metric_key` / **`formula` = 一段 SELECT SQL** / `refresh_cron`）+ `statistics_data`（`metric_key` / `value` / `dimension` / `stat_date`）。
→ **指标注册进这里，复用现有定时刷新机制**，不另起 ETL，天然满足"口径可追溯"。

**指标清单**：

| 指标 | 口径 | 是否进人才选拔 |
|---|---|---|
| 提问量排行 | 按人 / 部门去重计数 | ❌ 仅观察 |
| 有效问题率 | 被问方确认有效 / 总提问 | 观察 |
| 部门被问排行 | 按 `owner_department_id` 计数 | ❌ 以"职责模糊地图"形态输出 |
| 被问者**响应力** | 首次已读时长、首次回复时长、**已读未回复率**（v3：无红线，看分位分布） | ✅（作画像维度，不作扣分项） |
| 被问者**解决力** | 解决率、二次转办率、reopen 率 | ✅ |
| **知识沉淀贡献** | 沉淀为知识条数量 + 被复用次数 | ✅ |
| **提问价值** | 见 §3.9 的三层漏斗 | ✅ |

**反刷量铁律**：进榜指标必须有**下游动作背书**——已解决 / 被问方确认有效 / 沉淀为知识并被复用 / 提问方有效评价。单纯"答得多""问得多"不计分。

### 3.9 「全员公开」的呈现设计（D3：全员公开，**形态已确认按本节执行**）

已定全员公开，但**"公开什么形态"比"是否公开"更决定成败**。

**✅ 公开（推荐）**

| 榜单 | 形态 | 目的 |
|---|---|---|
| **帮助榜** | 被感谢次数、解决问题数、知识沉淀条数 | 正向，激发助人 |
| **知识缺口地图** | 高频问题 TOP10 + "建议沉淀为知识" | **改进导向，保护被问方** |
| **提问榜** | 谁最爱提问 / 求助 | 正向标签（爱学习），不是负面 |
| **平台大盘** | 提问量、解决率、平均响应时长趋势 | 让全员看到系统在变好 |

**❌ 建议不公开**

- 个人拖延明细、**"已读未回复"点名**、未解决率排名（v3：已无催办/超时类指标，此处对应改为已读未回复）

**理由**：全公司盯着"谁读了不回"，会直接催生推诿——部门开始互相踢皮球，**甚至会让人"干脆不点开"来规避留痕**。
**被问量高应被解读为"这里缺知识 / 缺流程"，不是"这里的人不行"。** 这句话建议直接写进看板顶部。

**分阶段**：第 1 个月只公开正向榜 → 运行 1 个月后再评估是否加责任类维度（给组织一个适应期）。

**提问价值的三层漏斗**（不是单一加权分）：

| 层级 | 指标 | 数据来源 | 用途 |
|---|---|---|---|
| L1 | 提问总量、去重问题数 | `issues` | 仅观察 |
| L2 | 有效问题率 = 被问方确认有效 / 总提问 | `issue_events` | 定位是否"乱问" |
| L3 | ①被解决 ②沉淀为知识并被复用 ③触发新责任关系/流程改进 | `issues.status` + `contents` 关联 | **进选拔** |

### 3.10 「小管家」系统号（D6）

**定位**：平台官方服务号。既是**推送通道**，也是**数据入口**。

**实现方式**：在 `public.people` 增加一条 `role_type = 'bot'` 的记录（如 `id = 'bot-butler'`，`name = '小管家'`）。这样**通讯录、会话、消息、头像、搜索体系全部天然复用**，不用另建一套账号系统。

**三个能力**：

| 能力 | 说明 | 举例 |
|---|---|---|
| ① 主动通知 | 以会话消息形式推送给相关人 | 立项确认、问题已解决通知、转办通知 |
| ② 报表推送 | `msg_type='report_card'`，卡片内含预览 + 跳转/附件 | 每周一早 9:00 给领导推周报卡 |
| ③ 数据问答 | 跟小管家对话，返回数据卡片 | 领导问"本周哪个部门被问最多" → 返回知识缺口地图卡 |

**每个用户与"小管家"有一条常驻会话**（置于左栏常驻区），类似飞书服务号。

**权限铁律**：小管家**只能推给你有权看的内容**——领导看全公司，员工看自己。这条要在服务端强制校验，不能靠卡片隐藏。

**与「AI 助手」的分工**（两个都是左栏常驻项）：

| 入口 | 职责 |
|---|---|
| **AI 助手** | 找人与知识问答（就是现在的 `/ask`，左侧会话记录 + 右侧提问框结构保留） |
| **小管家** | 通知、报表、数据问答（**v3 起不含催办**——已随 D2 移除） |

→ 职责分开的好处：**通知流与对话流不混在一起**（否则领导的重要报表会被几十条提问刷掉）。

### 3.11 文件存储：本地磁盘设计（D5）

**存储路径（内容寻址，天然去重 + 秒传）**：

```
/data/fpim/files/{yyyy}/{mm}/{sha256[0:2]}/{sha256}.{ext}
```

逻辑：上传时先算 `sha256`，命中已有文件直接复用（秒传）；未命中才落盘。`im.attachments.storage_key` 存相对路径。

**访问方式**：nginx 直接静态服务，配**签名 URL**（带过期时间 + HMAC），避免裸链被外传。

**必须配套的四件事**（否则本地磁盘会出事故）：

| 项 | 建议 |
|---|---|
| **备份** | 本地磁盘**必须**做定时备份（rsync 到另一台机 / 快照）。磁盘挂了 = 聊天记录里的文件全丢，而文件是"留痕"的核心资产 |
| **配额** | 单人总量上限（如 5GB）+ 单文件上限（建议 100MB）+ 禁止可执行文件后缀白名单制 |
| **预览** | 图片生成缩略图；office/pdf 不强求在线预览，先做"下载打开" |
| **多实例风险** | ⚠️ 现在是单实例，本地盘没问题；**将来若扩多实例，本地盘无法共享，必须换对象存储**。架构上把存储访问收敛到一个 `storage` 接口，方便日后替换 |

#### 容量估算与备份归口（D5 落地必答项）

选了"文件存本地"，就必须回答两个运营问题——**要多大**、**谁来兜底**。这不是技术选型，是要向 IT 争取的资源。

**① 容量：建议起步 1TB 独立分区**（按 208 人推算）

| 假设 | 数值 |
|---|---|
| 人均日发附件 | 3 个 × 平均 500KB ≈ 1.5MB/人·天 |
| 全员日增量 | ≈ 312 MB/天 |
| 年增量（250 工作日） | ≈ **78 GB/年** |
| 含视频/大文件放大 2~3 倍 | **150 ~ 250 GB/年** |

→ **建议按 1TB 预留（约 4~6 年量），并配磁盘水位监控**（>80% 告警）。
⚠️ **磁盘写满的后果**：消息仍能发（消息体不含文件），但**附件上传全挂** —— 而附件恰好是"留痕"的核心内容。所以水位告警不是可选项。

**② 备份：必须有人兜底，且必须覆盖两样东西**

> 常见误区：以为"文件存本地"只需备份文件。**错。** 真正不可再生的其实是 **PG 数据库**（消息正文、`issue_events` 事件流、`issues` 状态）——文件没了还能重发，**事件流没了，考核与报表的历史就永久断了**。

| 方案 | 说明 | 推荐度 |
|---|---|---|
| **A. 并入 IT 现有备份体系** | 问 IT：有没有现成的定时备份/快照机制，能否把"PG 备份 + 文件目录"一起纳入 | ⭐ 首选（责任清晰） |
| **B. 挂 NAS / 共享存储** | 若公司已有 NAS，直接把文件目录放上去，天然带冗余 | ⭐ 次选 |
| **C. 系统自建 rsync 定时同步** | 自己写个定时任务同步到另一台机 | 兜底（要自己保证有人在看告警） |

**三个必须问清的问题**（建议直接照抄去问 IT）：
1. PG 数据库现在有没有定时备份？备份文件存哪、保留多久、**做过恢复演练吗**？
2. 文件目录要不要纳入同一套备份？由谁负责配置和监控？
3. 有没有 NAS 或共享存储可挂载？如果有，B 方案比 C 方案省事得多。

> **一句话**：技术方案我已经做完（内容寻址 + 签名 URL + `storage` 可替换接口），**剩下的 1TB 磁盘和备份责任人是资源问题，得有人拍板**。

### 3.13 消息搜索方案（D11：中文分词扩展只是"可选优化"，不阻塞开工）

**问题的由来**：PostgreSQL 自带的全文检索是按**"词"**切分文本的。英文有空格，天然分词；**中文没有空格**，PG 的默认解析器会把一整句中文当成一个 token —— 结果就是**搜不出来**。所以在 PG 上做中文检索，通常要装 `zhparser` 或 `pg_jieba` 这类**中文分词扩展**（这俩是 C 扩展，需要数据库管理员编译安装）。而现有库只装了 `pg_trgm`（三元组模糊匹配），没有中文分词扩展。

**这个顾虑其实有三种解法，只有第一种需要求人**：

| 路线 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. DB 装中文分词扩展** | `CREATE EXTENSION zhparser` → `to_tsvector('chinese', body)` + GIN 索引 | 效果最好：按词检索、相关度排序、关键词高亮 | **要 DBA 编译安装**；托管/云 PG 可能不给装；版本升级要跟着维护 |
| **B. 应用层分词 + PG 原生能力** ⭐ | Python 侧用 `jieba` 分词 → 写入 `im.messages` 一个额外列 → PG 用内置 `simple` 配置建 GIN 索引 | **完全不依赖 DB 扩展**；分词器可控可换；PG 原生能力，稳定 | 多一列 + 写入时多一步；词库升级需重建索引 |
| **C. `pg_trgm` 模糊匹配** | `body ILIKE '%关键词%'` + GIN trgm 索引（**现在就能用**） | 零依赖、零改表 | 没有"词"的概念，**无法相关度排序**；用户输入整句（如"怎么报销"）会搜不到；索引偏大 |

→ **推荐：首期用 C 保证功能不缺（半天工作量），P1 换 B 提升体验；A 只在 DBA 点头时才考虑。**
**结论：这条不需要开工前等 DBA 回话，可以并行推进。**

#### 比索引技术更重要的一件事：**先定搜索范围**

技术选型之前，先定"**允许搜多大范围**"，因为范围决定数据量，数据量决定技术必要性：

| 范围 | 建议 |
|---|---|
| 会话内搜索 | ✅ 必做，无隐私问题，数据量极小 |
| "我参与的会话"范围搜索 | ✅ 推荐做，覆盖 90% 真实需求 |
| 全员全局搜索 | ⚠️ **加权限过滤 + 范围限制**。全公司互相搜历史消息有隐私风险，建议限"我参与的会话 + 部门内公开群" |
| 审计级检索（管理员） | 复用 `public.audit_logs` 机制，**必须留审计日志** |

> **一句话**：把范围收敛到"我参与的会话"，即便用最土的方案 C 也够快；真正的风险不是性能，是**让员工能搜到与自己无关的私人对话**。

### 关键结论（供后续 FpIM IM 化重构复用）

- findperson = 「首问责任平台」，四层架构：Vue3 前端 / backend(FastAPI:8001，业务唯一写入方) / agent-service(FastAPI:8100，只读只推理只产草稿) / PG(public+agent+rag 三 schema) + OKF 知识仓库。
- agent-service 是核心资产：约 8,100 行 Python，209 个测试；主链 9 节点
  Intent → QueryStructurer → ConceptLinker → [Structured ∥ Knowledge 双路检索] → Merger → Ranker → RelatedPeopleFallback → ConfidenceGate → AnswerBuilder。
- 标签三层模型（RawTag → Concept/别名 → 人员-标签关系）+ 六级候选召回；只有确定性命中自动 resolved，trgm/向量只出候选。
- 排序确定性可解释，按 query_type 选 policy；正式责任证据优先级最高（responsibility_policy 下有正式责任直接 10.0）。LLM 不允许重排 Ranker 输出。
- 写操作走确认卡闭环，Agent 不写业务表；三类卡 profile/review/content。
- 两个向量空间严格隔离：Concept 512 维（bge-small-zh）、RAG 1536 维（text-embedding-v4）。
- 重要既有约定（FpIM 重构时必须继承）：
  1. AI 只产草稿，业务写入必经业务层；
  2. 分层降级是设计的一部分，新链路（WS/报表/催办）也要补降级；
  3. 两个向量空间不要合并。
- 现成可复用：组织树/人员名录/推荐理由机制/AGUI SSE 契约/全链路 Trace（可作"提问价值、部门被问排行"数据源）。
- 需新增：IM 核心（WS 长连接、消息可靠性、已读回执）、问题闭环状态机与催办、统计报表、HR 联动。
- 仓库自带 30 份模块设计文档（agent-service/docs/modules/），质量很高，是最好的深入入口。

### 关键事实核查结论（重要：已验证，别再搞错）

- ❌ 仓库**不存在** `issues` 表 / `mail_inbox`。Kimi 的 proposal.md 这两处表述是错的，已在其文档内加「六、勘误」修正。
- ⚠️ 全库检索证实：无 IM、无 WS、无文件上传接口、无 MinIO、无邮件设施。问题闭环 / 催办 / 报表 / 上传 / 推送**全部需新建**。
- ✅ PG 只用了 `pg_trgm`，**没有** zhparser / pg_jieba → 中文全文检索需 DBA 装扩展，是已知风险点。
- ✅ **命名冲突**：`public.sessions` / `public.messages` 已被 AI 问答占用（backend /api/v1/sessions）。IM 表必须另起，方案定为新建独立 schema `im`。
- ✅ **免费午餐**：`public.responsibility_assignments` 已存 `time_limit` / `transfer_condition` / `escalation_path`；`public.people.manager_id` 已有（带触发器同步）。催办升级规则的**数据基础已存在，只是从未用于运行时**。
- ✅ `public.statistics_definitions`（`formula` 是一段 SELECT SQL + `refresh_cron`）+ `statistics_data` = 现成的可扩展统计框架，报表指标应注册进这里而非另起 ETL。
- ✅ 原设计文档已经"预留"了这次需求：`功能详细说明v4.md` §十五 + `实施方案.md` 开篇均显式把「工单办理、跨部门转办、催办升级」列为**延后功能**。这次重构 = 启用第二期。
- ✅ 复核 GitHub API：JuggleIM `im-server` ★3553 / Fork 372 / Apache-2.0 / Go / 2026-09-17 当日有推送，与 Kimi 记录一致。

### 我在方案里的主要判断（与 Kimi 不同处）

1. **推荐自研 IM，非 JuggleIM**。决定性理由：报表/催办/人才画像全是 SQL 聚合，消息必须和 issue 同库同事务；外部 IM（MySQL/Mongo）要加同步管道，必然产生"报表数字 ≠ 聊天记录"事故。
2. **"部门被问最多"口径换成"职责模糊地图"**。当排行榜会诱发推诿或刷量，违背"制造麻烦逼解决"初衷。
3. **issue 与 conversation 是 M:N**（Kimi 用 1:N `issues.conversation_id`）。落地用 `source_conversation_id` + `source_message_id` 锚点 + `current_owner_id` 双指针。
4. **`issue_events` 作唯一事实源（轻量事件溯源）**，`issues` 只是投影 → 报表口径可追溯到事件，满足 v4 §十二 既有要求。
5. **问题闭环层应对标 helpdesk（Zammad SLA/Escalation、Chatwoot 会话生命周期），而非 IM**。
6. **分期改为双线并行**：P0-a IM 内核 ∥ P0-b 问题闭环，P1 汇合。个人主页合并从 P1 挪到 P2（要等 issue 数据先跑起来）。
7. **补充组织推行策略（软启动）**：只对上公布不对下公示、先上答谢再上考核、部门榜以"知识缺口地图"形态输出、IT/HR/行政试点、时限从宽到严。
8. **IM 协议六件套开工前必须定死**：bigserial 游标排序（不用时间戳）、client_msg_id 幂等、ack 重发、增量拉取（不做离线队列）、游标式已读（不做逐条回执）、Redis pub/sub 扩容。

### 本轮新增的设计要点（重要）

- **术语教训**：用户不认识「催办」这个词（OA 老词，意为"催对方赶紧办"）。方案里已改称「**超时提醒与升级**」。→ 后续给这个用户写材料，避免 OA/政务行话。
- **响应时限 vs 解决时限必须分开**（默认 24h / 72h）。只考核解决会诱发"拖回复"和"假解决"；分开后机制逼的是"别装死"而非"别接活"。这是 Zammad 一类 SLA 的标准做法。
- **延期机制**：责任人可申请延期（填理由 + 记 `issue_events.extended`），批后重算时限。
- **群聊的责任归属必须唯一**：群问题不能归"群"，立项时必须从群成员中指定唯一责任人（默认群主），否则"集体负责=无人负责"，考核基础塌陷。
- **「小管家」与「AI 助手」分工**：小管家 = 通知/催办/报表/数据问答；AI 助手 = 找人与知识问答。分开的好处是重要通知不被提问流刷掉。
- **D1 与 D6 强绑定**：小管家在 IM 内推报表，只有消息与报表同库才干净 —— 这是选自研最强的理由。
- **P0 变重**，拆成三条并行轨道（A IM 内核含群聊 / B 问题闭环 / C 桌面壳）。超时升级调度器放 P3（依赖先稳定且数据量起来前意义有限）。
- 仍需确认 4 条：超时默认值、延期审批权归谁、群聊人数上限、HR 联动契约。
- 行动项：问 DBA 能否装 `zhparser`/`pg_jieba`；确认文件存储磁盘规划与备份归属。

### 本轮关键设计（重要，别再改回去）

- **已读/未读必须双存储**：`im.conversation_members.last_read_message_id`（会话级，会被覆盖，供 UI 红点）+ `issue_events.read` / `issues.first_read_at`（问题级，只记第一次，永不覆盖，供报表留痕）。用游标当证据 = 证据会被冲掉。
- **只认责任人的已读**：群聊里其他人读过不算，否则"群里都看了"会掩盖"责任人没看"。转办后新责任人另记一条 read。
- **`resolved` 只能由提问方确认**，被问方不能自评 —— 这是去掉时限后最容易被钻的漏洞。
- **报表口径从"达标率"改为"分位数分布"**（无时限就不能有"达标"概念）。新增核心风险指标：**已读未回复率**。
- **砍掉超时机制是"可逆"的**：`first_read_at` / `first_response_at` 从现在起就在积累，加上 `responsibility_assignments.time_limit` 等既有字段，日后恢复只需加调度器 + 2 个 due 字段，schema 不用重构。这是敢砍的底气。
- **中文检索三条路线已定**：A 装 DB 扩展（求 DBA）/ B 应用层 jieba 分词 + 原生 tsvector（不依赖扩展，推荐 P3 上）/ C `pg_trgm`（现成，首期用）。**结论：不必等 DBA，可并行推进。** 另注：比索引技术更重要的是**先定搜索范围**（默认限"我参与的会话"）。
- **文件存储两个必答项**：① 容量按 208 人测算 ≈ 78GB/年（含大文件放大 150~250GB/年）→ 建议 1TB 独立分区 + 水位告警 ② 备份要覆盖 **PG 数据库（比文件更关键）** + 文件目录，需确认归口。
- **无自动催促后，公开看板是唯一牵引力** → P3 地位上升。

### 范围外（明确不做，避免误排期）

### 技术要点（写代码时直接用）

- **关键实现技巧**：单聊幂等用 `INSERT ... ON CONFLICT (direct_key) DO UPDATE RETURNING id` 一步查或建；首次已读用 `ON CONFLICT (issue_id, actor_id) WHERE event_type='read' DO NOTHING` + 部分唯一索引 `uq_ev_read_per_actor` 保证只记一次；消息幂等靠 `UNIQUE(sender_id, client_msg_id)`。
- **写入顺序**：先写事实（`issue_events`），再更新投影（`issues`）。反了可能"投影说有、事件查不到"。
- **WS 网关建议单独单 worker 进程**（连接注册表在进程内）；HTTP 可多 worker。
- 监控必配**磁盘水位告警**（盘满 = 附件不可用）。

### 前端设计约定（后续保持一致，勿改）

- 状态色：未读 #F54A45(红) · 已读未回复 #FF8800(橙) · 处理中 #3370FF(蓝) · 已解决 #34C724(绿) · 未解决 #8F959E(灰)
- 布局：导航栏 68px / 列表栏 300px（可拖 240~400）/ 顶栏 56px；窗口最小 **1024×700**；默认 1280×800
- 导航 6 项：消息 / 通讯录 / AI 助手 / **待办** / 看板 / 设置（「待办」是为被问方设的独立入口，未读置顶 + 左侧红条）
- **问题卡的「进展」行**（未读 / 已读未回复 / 已读 X 分钟后回复）是留痕机制在 UI 上的唯一出口，必须有

### 关键结论：飞书的四个视觉基因（返工原因就在这）

1. **白底为主** —— 只有左栏浅灰，内容区全白。上一版做成"大灰底 + 白卡片浮起"，方向就错了。
2. **极轻分隔** —— 一律 `0.5px` 线、透明度 9%~14%，**几乎不用阴影**。上一版 1px 深边 + 阴影 = 视觉噪点。
3. **四级灰严格分层** —— `#1F2329` / `#646A73` / `#8F959E` / `#BBBFC4`，正文用一级灰不用纯黑，不滥用加粗。
4. **大留白、小圆角** —— 行高 1.6，圆角 6~10px（只有窗口外层 14px）。禁 20px+ 圆角。

### 已校准的尺寸（文档 §12.2 与原型一致）

导航栏 **68px** / 列表栏 300px（可拖 240~400）/ 主内容区 flex / 详情面板 320px；标题栏 44px、会话头 56px；窗口默认 **1280×800**（最小 1024×700）。

### 与飞书必须不同的 5 处（照抄会出问题）

会话列表加「待办未闭环」分组 · 「待办」做独立导航项+红点 · 会话条目带状态标签 · 详情面板 = 问题详情+处理过程时间线 · **状态徽标必须带文字不能只用色点**（否则被读成"系统给我亮红牌"）。

### 会话内立项（「过程即数据」的最后一环）

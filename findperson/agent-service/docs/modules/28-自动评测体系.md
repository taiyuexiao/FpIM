# 模块 28:自动评测体系

## 背景

对应 V1.2 §16(自动评测体系):§16.1 Evaluation Runner(dev/test 分集,**开发只能用 dev 调参,test 冻结**,一条命令跑全量)、§16.2 节点级评测(**不只评最终准确率**,员工侧/查询侧概念映射分别评,每条错误可归因)、§16.3 Baseline 对照(A 纯结构化 / B 纯 RAG / C 双路+排序 / D Agent 全链 / E Concept 消融,**避免无法判断提升来自哪个模块**)。§21 验收基线要求「不得只以最终回答看起来正确作为上线验收」。

## 任务

- 输入:真实数据(300 人/61 领域/24 责任/30 文)
- 输出:评测集(dev/test)+ Runner + 节点级指标 + 错误归因 + 五基线对照报告
- 验收:harness 端到端可跑;指标覆盖节点级清单;失败案例可归因到具体节点

## 实现方式

- `scripts/generate_eval.py`:确定性生成(seed=42)52 条用例,按类型分层切 dev/test 各 26 条:contact_lookup×12(人名查电话)、explicit_responsibility/diagnostic/expert_finding 各 10(覆盖人数 Top10 领域)、knowledge_qa×10(责任知识+文章内容);gold 含 person_ids(自填+正式责任人)/concept_names/document_ids
- `app/eval/metrics.py`:`CaseResult`(预测+gold+归因);recall_at_k/hit_at_k;`MetricsAccumulator.summary()` 输出 §16.2 指标(Intent/QueryType Accuracy、Query→Concept Recall@3、Structured Recall@3、RAG Recall@5、Candidate Recall@5、Final Top1/Recall@3、OKF Citation Coverage、Error Attribution 分布);`attribute_error()` 按第一个出错节点归因(intent/query_type/query_concept/structured_recall/rag_recall/merge/ranking/answer)
- `app/eval/runner.py`:
  - 全链(Baseline D)用 `_GoldIntentService/_GoldIntentStructurer` 注入 gold 意图与结构化(意图准确率留给真实 LLM 单独评,避免 LLM 波动污染链路指标;contact_lookup 补 mentioned_people)
  - Baseline A(概念+TagMatcher)/B(纯 RAG 人员证据)/C(双路+Ranker)/E(raw_tag 字符串 LIKE,无 Concept 层)
  - `run_evaluation(split, baselines)` 一条命令出报告 → `data/eval/report_{split}.json`
- `scripts/run_eval.py --split dev --baselines A,B,C,D,E`
- **dev 集真实结果**(52 例中 26 dev):
  | 指标 | A 纯结构化 | B 纯RAG | C 双路 | D 全链 | E 字符串匹配 |
  |---|---|---|---|---|---|
  | Final Top1 | 0.714 | 0.667 | 0.714 | **0.810** | 0.0 |
  | Final Recall@3 | 0.714 | 0.762 | **0.857** | **0.857** | 0.381 |
  | RAG Recall@5 | — | 1.0 | 1.0 | 1.0 | — |
  | Citation Coverage | — | — | — | 1.0 | — |
  - **结论 1**:C/D > A/B,双路融合确有增益(§16.3 目标)
  - **结论 2**:E(0.381)≪ 概念对齐(0.857),**Concept 中间层价值被单独证明**(§16.3 Ablation 目标)
- 测试 `tests/test_eval.py`(4 用例):指标原语、错误归因分层、dev/test 互斥且 gold 完整、Runner 小子集端到端,全部通过(累计 137 passed)

## 遇到的问题报错及解决方法

1. **contact_lookup 用例在全链评测中全军覆没**:`_GoldIntentStructurer` 只注入概念名,而 contact_lookup 链路需要的是 `mentioned_people`(DirectorySearch 输入),评测脚手架与真实链路的输入契约不对齐。
   解决:评测 structurer 对 contact_lookup 用例从 gold person_ids 反查人名注入 mentioned_people;修复后 D 基线 Structured Recall@3 从 0.714 → 1.0,Final Top1 0.524 → 0.810。
2. **基线 A/E 的 contact_lookup 失败是预期行为**:contact_lookup 本就不走概念路径(§8.1),其失败在归因中如实呈现为 structured_recall_error,不粉饰指标。

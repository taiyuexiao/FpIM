# 首问责任平台实施方案 v3

## 一、总体架构

```text
前端（Vue 3 + Vite + Element Plus）
  ├─ 业务页面 ── REST ──> 业务后端
  └─ 智能问答 ── AG-UI SSE ──> Agent 运行时
                                   ├─ Hermes：意图判断、工具请求、回答组织
                                   ├─ 固定组件：会话记忆、标签匹配、证据排序、审计
                                   └─ MCP Client ── MCP ──> 知识 MCP Server
                                                               └─ RAG 服务
                                                                  ├─ OKF 知识仓库
                                                                  └─ PostgreSQL rag schema

业务后端 ── 业务变更/发布事件 ──> OKF 发布服务 ──> RAG 增量索引
源代码 ── Docker Build / 测试 / 扫描 ──> Harbor ──> 行内部署环境
```

### 1.1 组件职责

| 组件 | 主要职责 | 不负责的事项 |
|---|---|---|
| 前端 | 业务页面、AG-UI 事件消费、推荐与引用展示、确认和反馈交互 | 业务鉴权裁决、知识检索 |
| 业务后端 | JWT 鉴权、业务 CRUD、责任关系事实源、OKF 发布触发 | Agent 推理、向量检索 |
| Hermes | 输出结构化意图、工具调用请求和带引用的回答 | 直连数据库、文件系统、Embedding 服务 |
| Agent 运行时 | Harness、TagMatcher、PeopleRanker、SessionMemory、MCP 客户端、Agent 审计 | 直连 rag schema 或 OKF 文件 |
| 知识 MCP Server | 向 Hermes 暴露只读知识工具 | 业务写操作、Agent 推理 |
| RAG 服务 | OKF 解析、1536 维 Embedding、混合检索、权限过滤、引用、索引任务 | 最终回答生成、标签精确匹配 |
| OKF 仓库 | 保存治理后的责任事项、人员、部门、流程、制度、FAQ、内容与关系知识 | 在线检索、运行态会话 |
| PostgreSQL | 保存业务事实、Agent 运行数据、RAG 派生索引 | 取代 OKF 作为正式知识发布物 |
| Redis | JWT 黑名单、登录限流、热点缓存 | 持久化业务事实 |

### 1.2 调用与权限边界

| 调用方 | 被调用方 | 协议 | 约束 |
|---|---|---|---|
| 前端 | 业务后端 | REST/JSON | Bearer JWT |
| 前端 | Agent 运行时 | AG-UI SSE/HTTP | 后端或网关签发可信 user_context |
| Hermes | 知识 MCP Server | MCP | 仅由 Harness 校验后发起 |
| MCP Server | RAG 核心 | 进程内或内部 HTTP | 不向前端公开 |
| RAG | OKF 仓库 | 受控 Git 工作副本或只读挂载 | 读取已发布知识 |
| 业务后端 | OKF 发布服务 | 内部 REST 或消息事件 | 业务发布或变更后触发 |

Hermes 本体不直连任何数据库与文件系统。Agent 运行时使用最小权限账号仅读写 `agent` schema；对 `rag` schema 和 OKF 的访问一律经 MCP。RAG 账号不得修改 Agent schema 和业务表。

## 二、技术栈

| 层次 | 选型 |
|---|---|
| 前端 | Vue 3、Vite、Element Plus、Pinia、Vue Router、Axios |
| 业务后端 | FastAPI、SQLAlchemy Async、asyncpg |
| Agent 运行时 | Hermes Agent、AG-UI 适配层、FastAPI、asyncpg、httpx、Pydantic |
| 知识 MCP | MCP Python SDK |
| RAG | FastAPI、asyncpg、pgvector、PyYAML、Markdown Parser、httpx |
| 数据库 | PostgreSQL 15+、pgvector、pg_trgm |
| 缓存与任务 | Redis、APScheduler 或 Celery + Redis |
| 向量模型 | RAG使用行内批准的1536维Embedding服务；Agent概念匹配使用1024维Embedding，模型名与版本分别配置 |
| 检索 | PostgreSQL 全文检索、pg_trgm、pgvector、RRF、可选 reranker |
| 发布 | Docker/OCI、行内 Harbor |
| 可观测 | Prometheus 指标、结构化日志、统一 trace_id |

RAG与Agent分别管理自己的Embedding模型和索引版本。任一侧切换模型时只重建本侧索引，不得在同一索引版本混写不同模型或不同维度的向量，也不得跨索引空间比较或复制向量。

## 三、前端方案

### 3.1 路由与页面

| 路由 | 页面 | 功能 |
|---|---|---|
| `/login` | LoginView | 登录，独立布局 |
| `/ask` | AskView | 智能问答与 AG-UI 流式输出 |
| `/directory` | DirectoryView | 名片库 |
| `/mine` | MineView | 个人中心 |
| `/manual` | ManualView | 操作手册 |
| `/profile/:id` | ProfileView | 人员主页 |
| `/review` | ReviewView | 为他人画像 |
| `/publish` | PublishView | 内容发布或编辑 |
| `/content/:id` | ContentDetailView | 内容详情 |
| `/admin` | AdminView | 后台管理，仅管理员 |

规则：`/login` 使用独立布局；其他页面使用 `MainLayout.vue`。未登录用户访问业务页面跳转 `/login`；已登录用户访问 `/login` 跳转 `/ask`。路由守卫先执行 `auth.bootstrap()` 恢复并校验登录态，通过后再加载人员、内容、评价和会话数据；401 统一清理失效登录态并返回登录页。人员与内容详情必须有真实 URL。内容发布表单不得出现“内容类型”字段。

### 3.1.1 页面行为与导航

登录后的主导航固定展示“智能问答”“名片库”，管理员额外可见“后台管理”；个人中心、修改密码、操作手册和退出登录由右上角用户菜单进入。主导航仅切换页面，不创建会话、不清空搜索条件、不提交业务数据。

`/ask` 采用历史对话栏、主对话区和右侧详情栏的三栏独立滚动布局。历史栏固定显示当前用户的全部会话，支持新对话、关键词搜索、重命名和删除；已有空白会话时复用，删除全部历史后仍保留可用空白会话。详情栏默认隐藏，点击人员、内容或待确认卡片后展开；关闭前保留当前对象。

名片库支持关键词与部门树的组合筛选，部门节点命中自身及全部下级部门人员。人员主页展示人员、上级、部门职责、画像和已发布内容；个人中心展示本人所有内容状态，并承接资料维护、画像、发布和本人内容管理。详情、发布和画像页面使用 `redirect` 保存完整内部来源路由，无来源时返回默认上级页；资料编辑、画像和发布存在未保存修改时拦截普通页面离开，但登录失效和主动退出必须直接放行。

后台管理采用“数据看板、成员管理、内容审核”三个页签。看板固定展示参与人员数量、已发布内容、待审核内容、本周推荐量、本周推荐热度排行和周日活趋势；参与人员数量按当前启用成员统计，停用成员不计入人数和新的推荐。

### 3.2 Store 与服务层

| Store | 职责 |
|---|---|
| `auth.js` | 登录、退出、密码、当前用户、个人资料 |
| `app.js` | 布局、加载、错误、侧栏状态 |
| `sessions.js` | 会话列表、消息、搜索、重命名、删除 |
| `agui.js` | 运行状态、流式消息、推荐卡片、确认卡片、详情栏、反馈 |
| `directory.js` | 人员、部门树、筛选、人员详情 |
| `content.js` | 内容列表、详情、发布、编辑、删除、置顶 |
| `reviews.js` | 发出与收到的评价 |
| `admin.js` | 指标、热度排行、活跃趋势 |
| `feedback.js` | 回答与推荐反馈 |
| `drafts.js` | 资料、画像和内容草稿；按 `draftId` 保存、读取和清理 |

前端保持 mock/server 双模式：业务接口由 `VITE_API_MODE` 控制，问答接口由 `VITE_AGUI_MODE` 控制；组件不感知两种模式的返回差异。AG-UI 处理层由 `transport.js`、`normalizer.js`、`reporter.js`、`mockStream.js` 组成。

`auth.js` 不保存用户密码，仅保存演示模式必要的登录标识；Server 模式启动时调用 `/me` 校验现有 Token 或 Cookie。`http.js` 统一规范化接口错误，401 触发登录态清理。`content.js` 提供对象级可见性解析：所有者和管理员读取当前版本，其他用户仅读取已发布内容；当前版本待审核或被驳回但存在 `publishedSnapshot` 时，其他用户读取最近已发布快照。

`drafts.js` 保存问答确认卡生成的纯数据草稿，URL 仅携带 `draftId` 和 `redirect`。资料草稿进入个人中心编辑态，画像草稿进入 `/review`，内容草稿进入 `/publish`；保存成功后删除草稿。`navigation.js` 只接受站内绝对路径作为返回目标，拒绝协议地址和双斜杠地址。

### 3.3 AG-UI 事件与接口

Agent 接口：

| 接口 | 用途 |
|---|---|
| `POST /agent/chat` | `query + session_id`，返回 AG-UI SSE |
| `POST /agent/feedback` | 提交带 trace_id 的推荐反馈 |
| `GET /agent/feedback/reasons` | 获取点踩原因配置 |
| `GET /agent/tag-policy` | 获取标签模板和最低标签规则 |

前端统一消费 `run_started`、`text_delta`、`text_finished`、`recommendation_cards`、`confirmation_card`、`state_delta`、`run_error`、`run_finished`。每个运行事件必须带 `sessionId` 和 `runId`，消息事件必须带 `messageId`。

前端只负责展示消息角色、卡片、引用和交互，不以客户端数据自行判断用户部门、角色或知识访问权限。

#### 卡片与事件契约

`recommendation_cards` 对找人类问题最多返回三人，按“首推、可协助、相关人员”展示。每张人员卡必须包含人员标识、姓名、完整部门路径、岗位、领域标签、联系方式摘要、证据层级、推荐理由和人员主页入口。理由须说明命中的正式责任、负责领域、画像、已发布内容或组织关系，不得只返回抽象匹配分数。

`confirmation_card` 用于资料维护、内容发布和他人画像写操作，必须包含卡片标识、动作类型、待写入字段、状态和提交目标。确认成功后卡片转为完成状态并禁止重复提交；内容确认只提交审核，前端成功提示不得表述为已经公开发布。手动补充创建 `draftId`，跳转到对应页面并回填草稿。所有事件按 `sessionId`、`runId`、`messageId` 归属，客户端切换会话或刷新后不得串写事件。

回答与推荐人员卡片均提供互斥的有帮助/没帮助反馈。推荐反馈必须带 `session_id`、`message_id` 和 `trace_id`；内容或人员轻量反馈不得替代该推荐反馈。

### 3.4 前端安全与状态约束

浏览器不得持久化密码。前端的菜单隐藏、路由限制和内容可见性过滤只用于交互防护，生产环境的账号状态、管理员权限、内容对象权限和字段过滤仍由业务后端裁决。停用成员不得登录，不进入新的人员推荐、参与人数、本周推荐量和热度排行。

内容删除、画像事项删除和审核通过执行二次确认；审核驳回必须填写原因。置顶操作仅对当前用户本人且状态为已发布的内容开放。他人画像提交校验评价对象不是本人、日期非空、事项非空且不超过 20 个字符。

### 3.5 构建与前端验收

业务路由使用动态 `import()` 按页面拆分，Element Plus 组件按需注册。当前构建入口 JavaScript 已由约 1.21 MB 降至约 588 KB，后续可继续拆分表格与公共依赖；CSS 和依赖版本由锁文件统一管理。

`npm run build` 是提交前构建门槛。`npm run smoke -- <URL>` 使用独立浏览器数据目录执行登录、问答、会话、详情、名片库、个人中心和草稿流程，并验证普通成员无法读取他人非公开内容、待审核新版本仍返回旧公开快照、运行期间无 JavaScript 异常。

## 四、Agent 服务

### 4.1 总体流程

```text
用户问题
→ 接入适配：校验 user_context，生成或透传 trace_id，加载会话记忆卡
→ Hermes 首步结构化输出
  ├─ edit：下发确认卡片，调用业务后端或写 MCP
  ├─ chat：直接应答
  └─ find_person / knowledge_qa / unclear：
       路径 A 标签规则匹配 + 路径 B 知识 MCP 检索
       → 合并候选并按证据分级排序
       → Hermes 生成“事实 / 建议”分区回答与引用
       → AG-UI 流式输出
→ 记录反馈与更新会话记忆卡
```

### 4.2 意图与会话记忆

Hermes 首步输出由 Harness 使用 Pydantic 校验：

```json
{
  "intent": "find_person | knowledge_qa | edit | chat | unclear",
  "edit_action": "update_tags | update_profile | publish_content | submit_review | null",
  "keywords": ["Dify"],
  "mentioned_systems": ["Dify"],
  "symptoms": [],
  "query_type": "explicit_responsibility | diagnostic | expert_finding | concept_question",
  "needs_clarification": false,
  "clarify_question": null
}
```

LLM 为默认路由；LLM 不可用时使用 `RuleFallbackRouter`。规则仍无法命中时返回标明降级的关键词粗匹配结果或结构化错误，不编造负责人。

会话记忆写入 `agent.agent_sessions.context`，只包含 `locked_concepts`、`last_candidates`、`excluded_persons`、`pending_clarification` 和最近 3 至 5 轮摘要。单卡控制在 200 至 500 Token，30 分钟无活动或新建会话即清空，不做跨天记忆。

### 4.3 双路检索与排序

**路径 A：标签规则匹配。** Agent 运行时以概念、原始标签、复合标签组分和证据视图做 SQL 或内存匹配；该路径不调用 LLM。标签格式可为“系统-角色-职责”，例如 `HiAgent管理员-Key分配`。原始标签进入 `raw_tags`，人员关联进入 `person_tags`，语义归一通过 `concepts` 与 `tag_concept_map` 完成。

**路径 B：知识 MCP。** 调用以下 8 个只读工具：`search_knowledge`、`get_document`、`get_responsibility`、`get_person_profile`、`get_process`、`find_related_knowledge`、`list_sources`、`knowledge_health`。每次调用携带经签名或可信转发的 `user_context`，单工具建议超时 2 秒；连续失败后熔断并降级为路径 A。

PeopleRanker 合并两个路径的候选人，以最高证据层级排序：

| Tier | 证据 | 展示身份 |
|---|---|---|
| 1 | MCP `get_responsibility` 返回的正式责任人 | 正式责任人 |
| 2 | 自填标签映射命中概念 | 明确负责领域命中者，注明个人维护 |
| 3 | 画像或项目叙述推断 | 相关参与者 |
| 4 | 他人评价标签 | 能力候选人 |
| 5 | 文章作者关联 | 领域专家 |

高 Tier 始终优先于低 Tier；文章热度不得越过正式责任。Hermes 只解释排序结果，不重新排序。

### 4.4 写操作、输出与反馈

写操作仅通过业务后端或独立写 MCP 执行：`update_my_tags`、`update_my_profile`、`publish_content`、`submit_review`、`confirm_inferred_tag`。均要求权限校验、前端二次确认和 `audit_id` 返回。知识 MCP 保持只读。

回答必须区分“检索到的事实”和“Agent 的归纳建议”，并展示 `document_id`、版本和来源 URI。无正式责任依据时必须拒答或转人工，不得补齐负责人。

带 `trace_id` 的推荐点赞或点踩写入 `agent.feedback_events`；需要人工处理时关联 `agent.feedback_tickets`。不带 `trace_id` 的内容、回答或人员轻量赞踩保留在 `public.feedback`。两类反馈不双写，历史推荐反馈一次性迁移。

#### 内容与评价写入规则

`publish_content` 的用户确认只创建或更新内容草稿并提交审核，不直接对外发布。内容状态为 `draft → pending_review → published` 或 `draft/pending_review → rejected`；驳回必须记录原因、审核人和审核时间。已发布内容再次编辑后生成待审核版本，在新版本审核通过前继续展示最近已发布快照。仅已发布内容可在人员主页、问答详情和推荐证据中出现。

`submit_review` 必须校验评价对象不是当前用户且事项非空。相同评价人、评价对象和事项再次提交按更新原记录处理；“继续补充”回填并更新原记录，不新增重复评价。删除采用逻辑删除或保留审计记录，已删除评价不得参与画像聚合和推荐。

## 五、OKF、RAG 与 MCP 知识服务

### 5.1 OKF 知识模型

OKF 仓库采用 Git 管理，目录包含：

```text
knowledge-okf/
├── responsibilities/
├── people/
├── departments/
├── processes/
├── policies/
├── faqs/
├── contents/
└── relationships/
```

每份文档使用 YAML frontmatter 和 Markdown 正文，至少包含 `type`、`id`、`title`、`version`、`status`、`visibility`、`sensitivity`、`source_type`、`source_id`、`source_uri`、`updated_at`、`content_hash`。发布态文档还必须具备责任部门和来源信息。

业务数据库是人员、部门、内容和责任关系的事实源；业务发布或变更任务生成或更新 OKF。制度、流程和复杂关系可通过模板人工维护并使用 Git 管理。业务数据不得直接写向量表。

### 5.2 PersonProfile 向量化边界

| PersonProfile 成分 | 是否向量化 | 用途 |
|---|---|---|
| 正式职责与负责领域的叙述正文 | 是，独立 chunk，权重最高 | 正式责任与领域证据 |
| 自画像正文 | 是，独立 chunk，低权重 | 相关参与者证据 |
| 他画像聚合正文 | 是，独立 chunk，最低权重 | 能力候选人证据 |
| `raw_tags`、`concept_ids`、已确认推断标签 | 否，不进入OKF | 仅由Agent标签路径保存和使用 |
| 部门字段 | 否，仅元数据 | 权限和范围过滤 |

生成PersonProfile时，必须在写入OKF之前剔除`raw_tags`、`person_tags`、`concept_ids`、推断标签、标签权重和标签提示模板。这些内容不得进入OKF frontmatter、Markdown正文、RAG元数据或Embedding输入。自画像、他画像和负责领域属于人物资料，继续进入PersonProfile并按上表切片；标签精确匹配完全由Agent路径A处理。

### 5.3 发布、校验与索引

```text
业务数据或原始文件变更
→ 生成候选 OKF
→ YAML Schema、唯一 ID、文件名、链接、敏感字段校验
→ 合并正式 OKF 仓库
→ 增量索引
→ 检索冒烟测试
→ 发布索引版本
```

使用 `id + content_hash + version` 判断变化。新增时写入文档与 chunk；正文修改时替换旧版本 chunk；仅元数据修改时更新权限与过滤字段；删除或废止时将在线索引设为失效；全量重建必须以新的 `index_version` 验证后原子切换。

### 5.4 解析、切片与检索

RAG 解析 YAML、Markdown 标题和关系文档；`index.md`、`log.md` 不作为普通正文向量化。责任事项按事项定义、处理要求、步骤、转办条件、时限和制度依据切片；人员按上述边界切片；流程按完整步骤链或阶段切片；制度按条款切片；FAQ 一问一答一片；内容按章节切片，超过 500 字再按句子切分并保留 overlap。

查询流程：

1. 接收 MCP 传入的查询、可信用户上下文和过滤条件。
2. 规范化查询并识别事项、人员、部门、字段和业务域线索。
3. 在关键词与向量召回前执行可见性过滤。
4. 并行执行全文/模糊检索与1536维向量检索，各召回top 20。
5. RRF 融合，二次权限复核，可选 reranker，按文档和章节去重。
6. 返回默认 top 5 的结构化片段、版本和引用，不生成最终答案。

Embedding、reranker 或 pgvector 故障时分别降级为关键词检索、RRF 排名或关键词结果。OKF 工作副本不可用时允许使用已发布索引，但禁止索引重建。空结果返回追问建议，不伪造知识结果。

### 5.5 MCP 与管理接口

知识 MCP 仅暴露第 4.3 节的 8 个只读工具。`get_responsibility` 必须返回首问受理部门、最终责任部门、责任人或岗位、办理时限、转办条件、升级路径、关联流程、制度依据、来源和版本。

索引维护仅使用内部管理接口：

| 接口 | 方法 | 用途 |
|---|---|---|
| `/internal/index/documents` | POST | 增量索引指定文档 |
| `/internal/index/documents/{id}` | DELETE | 从在线索引移除文档 |
| `/internal/index/rebuild` | POST | 创建全量重建任务 |
| `/internal/index/jobs/{id}` | GET | 查询索引任务 |
| `/internal/index/versions` | GET | 查询可用版本 |
| `/internal/index/publish/{version}` | POST | 发布已验证版本 |
| `/health/live` | GET | 存活检查 |
| `/health/ready` | GET | 数据库、模型、索引就绪检查 |

## 六、业务后端与权限

### 6.1 鉴权与可信上下文

登录签发 JWT，前端以 `Authorization: Bearer <token>` 调用业务接口。后端校验 JWT、Redis 黑名单和用户状态，并注入请求上下文。Agent 网关基于经过验证的身份生成或可信转发 `user_context`；MCP 不接受客户端自行声明的部门或角色作为授权依据。

权限过滤必须在 RAG 的全文与向量召回阶段执行，MCP 返回内容前再次校验。受限文档仅对明确授权的部门或角色可见。

### 6.2 业务接口

保留以下业务 REST 分类：鉴权、人员与部门、内容、评价、会话、轻量反馈和后台管理。人员接口使用 `/api/v1/people`；内容接口不含 `type` 字段；后台管理保留 `/api/v1/admin/metrics`、`/api/v1/admin/rankings/recommend`、`/api/v1/admin/trends/activity` 三个独立接口。

接口至少覆盖以下资源与授权规则：

| 资源 | 必要能力 | 服务端授权边界 |
|---|---|---|
| 当前用户与密码 | 查询本人、修改可维护资料、修改密码 | 用户只能更新联系方式、负责领域和自画像 |
| 人员与部门 | 名片查询、人员主页、部门树 | 普通用户只读可见字段；管理员维护成员、部门、负责人和账号状态 |
| 部门职责 | 查询、更新职责 | 仅部门负责人可修改本人负责部门及全部下级部门；管理员可维护组织关系 |
| 内容 | 草稿、提交审核、查询、编辑、删除、置顶、审核 | 所有者管理本人内容；仅管理员审核；置顶仅限本人已发布内容 |
| 评价 | 创建、更新、删除、查询发出/收到评价 | 禁止评价本人；仅评价人可更新或删除其评价 |
| 会话与消息 | 创建、搜索、重命名、删除、读取消息与卡片 | 会话、消息、卡片均按用户隔离 |
| 后台统计 | 指标、推荐排行、活跃趋势 | 仅管理员；统计口径可追溯到原始记录 |

成员停用后立即不能登录且不参与新的推荐；角色、负责人、审核、删除和停用操作均写入审计日志。接口返回的人员、内容和审核字段必须按当前身份过滤，前端隐藏按钮不得替代服务端授权。

责任关系以 `public.responsibility_assignments` 为唯一事实源，只由业务后端写入。业务变更后生成或更新 OKF `ResponsibilityItem` 并进入索引；Tier 1 正常查询走 MCP 的 OKF 发布索引。每日使用 `content_hash + version` 对账业务责任关系与 OKF 条目，差异告警；责任变更的检索可见延迟不超过 10 分钟。

内容、人员资料、部门职责、流程、制度与责任事项的发布、修改或废止均触发相应 OKF 更新与 RAG 索引任务，而非直接调用旧的 RAG ingest/delete/payload 公开接口。

## 七、数据库与数据归属

PostgreSQL 使用 `public`、`agent`、`rag` 三个职责边界清晰的 schema。向量扩展与 `pg_trgm` 由 DBA 安装；所有服务使用最小权限账号。

| Schema | 核心数据 |
|---|---|
| `public` | `departments`、`users`、`sessions`、`messages`、`contents`、`feedback`、`recommendation_logs`、`query_logs`、`statistics_definitions`、`manuals`、`peer_reviews`、`responsibility_assignments` |
| `agent` | `raw_tags`、`person_tags`、`concepts`、`tag_concept_map`、`concept_relations`、`agent_traces`、`query_concept_logs`、`agent_recommendation_logs`、`feedback_events`、`feedback_tickets`、`feedback_reason_options`、`agent_sessions`、`mcp_call_logs`、`intent_rules`、`tag_policy`、`v_person_concept_evidence` |
| `rag` | `rag_documents`、`rag_chunks`、`rag_index_jobs`、`rag_query_logs` |

`rag.rag_chunks.embedding`为`vector(1536)`，保存OKF文档向量；`agent.concepts.embedding`为`vector(1024)`，保存Agent内部概念归一向量。两者使用不同索引空间，禁止混写、复制或跨空间比较。Agent调用RAG时传递原始文本，由RAG生成1536维查询向量。

`rag.rag_documents` 保存来源路径、URI、版本、内容哈希、状态、可见性、敏感级别、授权部门、索引版本和生效状态。`rag.rag_chunks` 关联文档、章节路径、文本、全文检索文本、模型版本、Token 数、元数据和索引版本。`rag.rag_index_jobs` 管理 `pending → running → validating → published` 的索引任务。`rag.rag_query_logs` 仅保存脱敏查询摘要、过滤条件、召回文档 ID、耗时、降级状态和 trace_id。

`public.recommendation_logs` 保存业务侧逐人推荐日志，`public.query_logs` 保存业务查询日志。Agent 的 `agent.agent_sessions.context` 保存结构化记忆卡；`agent.mcp_call_logs` 与 `rag.rag_query_logs` 使用同一 `trace_id` 串联。详细推荐候选、排序快照和采纳结果写入 `agent.agent_recommendation_logs`，并由 `agent.v_person_concept_evidence` 为确定性排序提供统一证据视图。

### 7.1 业务对象与状态约束

`departments` 至少保存部门标识、名称、上级部门标识、完整路径、负责人标识、职责、状态和更新时间，部门树不得限制层级。`users` 至少保存系统角色、账号状态、岗位、所属部门和可维护的资料字段；上级关系由部门负责人链计算，不以岗位名称推断。

`contents` 至少保存发布人、标题、关联领域、摘要、正文、状态、当前版本、已发布快照、置顶状态、提交/发布/更新时间和审核轨迹。`peer_reviews` 至少保存评价人、被评价人、事项标签、评价日期、状态、创建/更新时间和审计字段。人员主页的他画像按有效评价的事项聚合，排序先按评价人数、再按最近评价日期。

`sessions` 和 `messages` 必须保存所属用户、会话/消息标识、标题或正文、创建/更新时间、运行标识、来源引用、推荐卡片和确认卡片关联。内容、评价、会话和消息的可见性与修改权限必须在业务后端校验，不依赖浏览器本地状态。

## 八、部署、安全与运维

### 8.1 镜像与发布

| 镜像 | 内容 |
|---|---|
| `first-responsibility/frontend` | Vue 静态资源与 Web Server |
| `first-responsibility/backend` | 业务 API 与 OKF 发布触发 |
| `first-responsibility/hermes-agent` | Hermes 配置、Harness、AG-UI 适配 |
| `first-responsibility/knowledge-mcp-rag` | MCP、RAG、OKF 解析与检索 |
| `first-responsibility/okf-validator` | OKF Schema、链接和安全校验 |

发布链路：代码提交 → 单元测试 → OKF 校验 → Docker 构建 → SBOM → 漏洞扫描 → 推送 Harbor 测试项目 → 测试环境按 digest 部署与验收 → 镜像晋级生产项目。

镜像使用固定基础版本、依赖锁文件、非 root 用户、多阶段构建和不可变版本标签。镜像不得包含密钥、OKF 私有仓库历史、测试数据或本地配置。OKF 正文通过只读卷、受控 Git 同步或受控制品方式提供，不与程序镜像绑定版本。

### 8.2 安全与审计

OKF 仓库必须使用内部私有 Git 或受控文件仓库。数据库密码、API Key 与 Harbor 凭据仅通过 Secret 注入。日志不得记录完整敏感文档、Embedding 输入全文、Authorization Header 或密码。

所有请求生成统一 `trace_id`，贯穿前端、Agent、MCP、RAG 与数据库日志。审计至少记录用户、工具、参数摘要、返回文档 ID、耗时和结果状态；最终回答记录所用的文档 ID 与版本，不重复保存敏感正文。

### 8.3 健康检查与回滚

所有服务提供 `/health/live` 与 `/health/ready`。镜像回滚使用上一个稳定 digest；知识回滚使用上一 OKF Git 版本和上一 `index_version`，二者独立执行。

监控指标包括 MCP 成功率与延迟、RAG 检索耗时与空结果率、索引任务与版本、Embedding 成功率、引用覆盖率、推荐采纳率、越权拦截次数、Agent 路径分布、Token 使用与反馈原因分布。

## 九、实施路线与验收

| 阶段 | 重点任务 | 验收结果 |
|---|---|---|
| 1. 工程与业务底座 | 前后端基础、PostgreSQL、Redis、业务 schema、鉴权与基础页面 | 业务页面可运行，权限边界正确 |
| 2. OKF 标准与样例 | 目录、YAML、正文模板、样例、校验器 | 样例可追溯且通过校验 |
| 3. RAG 最小闭环 | 1536维索引、解析切片、全文与向量检索、RRF、引用 | 标准问题返回正确事项、人员、流程和来源 |
| 4. MCP 与 Agent | 8 个只读工具、Hermes/Harness、标签路径、排序、AG-UI | 无结果不编造，推荐按证据分级输出 |
| 5. 发布与数据联动 | 业务变更到 OKF、增量索引、责任对账、反馈分域 | 内容、职责、权限和废止同步正确 |
| 6. 前端真实接入 | REST、AG-UI、引用、确认、反馈、会话 | 所有页面使用真实数据，问答体验完整 |
| 7. Docker 与 Harbor | 镜像、扫描、测试环境部署、回滚 | 按 digest 拉起并可回滚 |
| 8. 安全与质量验收 | 权限、敏感信息、注入、超时、降级、压力与评测 | 无已知越权路径，核心指标达标 |

验收底线：published OKF文档具有唯一ID、来源、版本、责任部门和`content_hash`；索引可回溯并可回滚；无权用户不能经向量、全文、缓存或引用读取受限内容；Embedding失效时可降级；正式责任人查询、引用和全链路trace可验证；RAG索引及查询向量均为1536维，Agent概念索引及查询向量均为1024维；标签数据不进入OKF或RAG。

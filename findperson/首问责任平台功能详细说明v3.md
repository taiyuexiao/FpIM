# 首问责任平台功能详细说明

本文档用于说明首问责任平台完整项目应具备的页面结构、功能组件、交互规则、业务状态和验收口径。后续无论由 AI 生成前端、后端、数据库、接口还是整体工程，都应以本文档描述的功能体验为准。

一、产品定位

首问责任平台的核心目标，是让用户遇到不清楚该找谁、需要维护个人信息、想发布内容或想评价同事时，可以先通过统一入口提出需求，由系统根据人员职责、个人画像、他人评价、发布内容和组织关系，推荐合适的首问责任人，并承接资料维护、他人评价和内容发布动作。

平台不是普通门户首页，也不是单纯人员通讯录，更不提供独立的内容检索能力。它的第一入口应是“智能问答”，通过对话承接用户问题，再把推荐合适的人、修改个人信息、为他人做评价、发布内容四类操作串联起来。用户不需要先知道部门归属，也不需要先进入多个模块查找。

整体体验应轻量、清晰、少跳转。页面应采用企业工具风格，左侧固定导航，右侧为主要工作区，信息排版紧凑但不拥挤。功能说明文字尽量少，重点放在可点击、可查看、可确认、可维护的业务动作上。

二、全局框架

平台采用左侧导航加右侧工作区的整体结构。左侧导航固定展示，不允许隐藏。右侧工作区顶部保留用户入口，下方展示当前页面内容。

左侧导航栏从上到下依次包含平台标识和四个主导航入口：智能问答、名片库、个人中心、后台管理。主导航只负责切换模块，不应附带业务动作。例如，点击“智能问答”只进入问答工作台，不应自动新建对话；点击“个人中心”只进入个人中心，不应自动打开编辑表单。

右上角用户入口展示当前登录用户头像和姓名。点击后展开下拉菜单，菜单包含个人中心、修改密码、操作手册、退出登录。未登录状态下只允许进入登录页；登录成功后进入智能问答。

登录页应居中展示登录卡片，支持账号、手机号或统一身份账号登录。登录成功后记录用户身份、权限、所属部门和个人主页信息。退出登录后清空当前会话访问状态，并回到登录页。

修改密码从右上角用户菜单进入，以弹窗形式展示，不跳转页面。弹窗包含原密码、新密码、确认新密码三个字段。提交时先校验原密码是否正确，再校验新密码长度和两次输入是否一致；校验失败时在弹窗内给出明确提示，修改成功后显示成功状态并关闭弹窗或允许用户手动关闭。

操作手册从右上角用户菜单进入，用于展示平台基础使用说明。页面内容以卡片形式呈现，至少覆盖登录与首页、智能问答与历史对话、名片库、个人中心与后台等使用场景。操作手册只承担查看说明的功能，不承载业务数据维护。

页面返回规则应符合用户直觉。主导航页面不需要单独返回按钮；二级页面如人员主页、内容详情、内容发布、他人评价可以保留返回按钮。系统应支持浏览器返回或应用内历史返回，避免用户在多次查看详情后迷路。

三、智能问答

智能问答是平台首屏和核心工作台。进入平台后，默认看到智能问答页面。页面内部横向分为三部分：左侧历史对话栏，中间对话区，右侧详情栏。右侧详情栏默认收起，只有用户点击问答结果卡片或手动打开时才显示。

历史对话栏位于智能问答页面内部左侧，不是全局导航。顶部显示“历史对话”，右侧放搜索图标和“新对话”按钮。下方列表展示用户历史会话，每条会话展示会话标题、对话轮次和当前选中状态。

点击“新对话”时，系统创建一个空白会话并切换到该会话。只有这个按钮能主动创建新会话。点击左侧主导航里的“智能问答”不应创建新会话，也不应清空当前对话。如果当前已经存在空白会话，应优先复用已有空白会话，避免连续创建多个无内容会话。

历史搜索通过弹出层完成。用户点击历史栏搜索图标后，在历史栏上方出现搜索框。输入关键词后，系统按会话标题、问题内容、回答摘要或意图类型筛选历史会话。点击搜索结果切换会话，按 Esc 或点击外部区域关闭搜索层。

历史会话应支持重命名和删除。每条会话右侧放“更多”按钮，点击后出现小菜单，包含重命名和删除。重命名只修改会话标题，不影响对话内容。删除后该会话不再出现在历史列表中。如果用户删除了最后一个可用会话，系统应自动保留或创建一个空白会话，确保智能问答始终有可继续使用的会话入口。

中间对话区顶部显示页面标题“智能问答”，右上角放详情栏开关图标。空白状态下，中间区域只显示“开始对话”四个加粗文字和底部输入框，不放复杂欢迎说明，不做大按钮式引导。

输入框固定在对话区底部。输入框为多行文本框，支持用户输入自然语言问题。右侧放蓝色“发送”按钮。按 Enter 发送，Shift + Enter 换行。空内容不允许发送。发送后输入框清空，并在对话区生成一轮用户问题和系统回答。

用户消息显示在右侧浅蓝气泡内。系统回答显示在左侧，先给出简短判断，再展示推荐卡片或待确认操作卡片。系统回答应尽量短，不堆砌大段说明。

智能问答应支持以下问题类型：

问题找人：当用户询问“谁负责、找谁、该问谁、谁能处理”时，系统返回推荐人员卡片。

资料维护：当用户表达修改个人信息、联系方式、负责领域、自画像时，系统生成资料维护确认卡。

内容发布：当用户表达想发布流程说明、常见问题、经验文章时，系统生成内容发布草稿卡。

他人评价：当用户表达想评价某位同事或补充他画像时，系统生成他人评价草稿卡。

四、问答结果卡片

人员推荐卡片用于展示系统推荐的首问责任人和协助人员。每张卡片展示姓名、部门路径、岗位、联系方式、负责领域、推荐标签、推荐理由和操作按钮。第一位人员标记为“首推”，第二位标记为“可协助”，第三位标记为“相关人员”。

推荐理由应具体说明为什么推荐该人员，例如负责领域命中、个人主页命中、他人评价命中、发布内容命中、近期被推荐次数较高等。理由应服务于用户判断，不要只写“匹配度高”。

人员卡片可以点击。用户在智能问答页点击人员卡片时，应在右侧详情栏展开人员详情，而不是直接跳转人员主页。人员卡片内的“查看主页”按钮可以进入完整人员主页。

资料维护卡片用于承接用户通过对话修改个人资料的场景。卡片展示识别到的修改项，并提供“确认更新主页”和“手动编辑”。如果系统已经识别出完整字段，用户点击确认后应直接完成更新，并同步个人中心、名片库和推荐逻辑；如果字段不完整，应提示用户进入个人中心补充。确认完成后，卡片应显示统一的已确认标记，标题和状态文案更新为已完成状态，主按钮从确认动作变为“继续编辑”或同类后续操作。

内容发布卡片用于承接用户通过对话生成发布内容的场景。卡片展示拟发布标题、类型、标签和摘要，并提供“确认发布”和“手动补充”。确认发布后内容进入内容库；手动补充时进入内容发布页，表单带入已生成内容。确认完成后，卡片应显示统一的已确认标记，按钮从“确认发布”变为“查看内容”或“继续编辑”等后续操作。

他人评价卡片用于承接为同事补充画像的场景。卡片展示评价对象、评价日期和事项草稿，并提供“确认保存评价”和“去我的主页修改”。确认保存时，事项草稿转换为事项标签并进入对应人员主页的他画像。确认完成后，卡片应显示统一的已确认标记，按钮从“确认保存评价”变为“查看评价对象”或进入个人中心继续维护等后续操作。

反馈按钮用于收集用户对回答和人员推荐的评价。问答回复和推荐人员卡片上的反馈对所有已登录用户可见。反馈形式为”有帮助 / 没帮助”，点击后切换选中状态，再次点击取消。反馈只作为当前用户行为记录，不应影响他人可见内容。

五、右侧详情栏

右侧详情栏是智能问答页的重要组件，默认隐藏。它只出现在智能问答页面的右侧，不应做成全局弹窗，也不应放到页面顶部。点击问答结果中的人员卡片或资料维护卡片时，详情栏展开。

详情栏顶部展示详情类型标签，例如“人员详情”“资料维护”。右上角有“收起”按钮。点击收起后详情栏隐藏，中间对话区恢复宽度，当前会话内容保持不变。

人员详情栏展示姓名、部门路径、岗位、联系方式、领域标签、自画像和相关发布内容。底部提供“查看主页”按钮，进入完整人员主页。

资料维护详情栏展示待更新字段、当前用户信息、确认按钮和手动编辑按钮。用户点击确认后应在当前问答页完成更新，不应强制跳转。

右侧详情栏不应在用户继续追问时自动清空。只要用户没有关闭详情栏，详情栏应保持当前查看对象，除非用户点击了新的卡片。

六、名片库

名片库用于查看平台内所有人员的职责名片。页面顶部只展示标题“名片库”，不需要说明性副标题，不需要返回按钮。

标题下方是工具栏。工具栏左侧是搜索框，右侧是三级部门筛选。搜索框支持按姓名、部门、岗位、职责、负责领域、自画像关键词检索。三级部门筛选包含一级部门、二级部门、三级部门，三个下拉框联动变化。

一级部门变化后，二级部门只显示该一级部门下的可选项；二级部门变化后，三级部门只显示对应范围。任一级选择“全部”时扩大筛选范围。人员列表必须同时满足搜索关键词和部门筛选条件。

人员以卡片网格展示。每张卡片包含姓名、完整部门路径、岗位、负责领域标签、自画像摘要和联系方式。整张卡片可点击。由于用户当前不在智能问答页，点击名片库人员卡片应进入人员主页，而不是打开右侧详情栏。

没有匹配结果时，列表区域显示空状态文案，提示没有匹配到人员名片。

七、个人中心

个人中心用于当前登录用户维护个人主页、发布内容、查看他画像和管理本人发布内容。进入个人中心时，默认展示个人摘要，不直接展示编辑表单。

个人摘要顶部左侧展示姓名、部门路径、岗位和联系方式。右侧展示三个操作按钮：编辑、为他人画像、发布。下方展示负责领域标签、自画像、他画像和“我的发布”列表。

点击“编辑”后，个人摘要隐藏，编辑表单显示。表单包含姓名、科室部门、职级/岗位、联系方式、负责领域、自画像。底部放“取消编辑”和“保存主页”。点击取消回到展示态，不保存修改。点击保存后更新个人主页，并同步名片库、推荐逻辑、右上角用户姓名和后台统计。

点击“为他人画像”进入事项添加页面。评价对象不包含当前登录用户本人，用户不能为自己补充他画像。页面包含同事、日期、事项、添加事项和取消按钮。

事项使用可搜索的下拉选择，候选项由被评价人的负责领域和已沉淀的他画像事项组成；用户也可以选择“其他”并填写不超过 20 个字符的自定义事项。未选择事项，或选择“其他”但未填写自定义事项时，不允许提交。提交后，记录写入被评价人员的他画像，并出现在当前用户“我添加的事项”列表中。

同一评价人对同一人员添加相同事项时，系统更新原有记录而不新增重复记录。“我添加的事项”按记录展示同事、日期和事项，并提供“继续补充”和“删除”操作；继续补充会带入同事、日期和事项，供用户修改后保存。

个人中心中的他画像不再截取最近 5 条，而是展示全部有效事项并按事项聚合为气泡图。为保持两栏视觉平衡，他画像区域高度随相邻自画像区域变化，最小高度为 350 像素。

点击“发布”进入内容发布页。发布页用于新增流程说明、常见问题、经验文章等内容。提交后内容出现在个人中心“我的发布”和人员主页中，并可作为后续推荐人员时的依据沉淀，但不形成内容检索功能。

“我的发布”展示当前用户发布的全部内容。标题右侧可放“筛选”按钮。点击后在该区域内展开一个只筛选本人发布内容的输入框；再次点击收起，并清空关键词。

本人发布内容应有显式管理按钮：置顶/取消置顶、编辑、删除。点击整张内容卡不应进入编辑。编辑必须通过“编辑”按钮触发；删除必须通过“删除”按钮触发；置顶只对本人内容生效。

八、人员主页

人员主页展示某个用户的公开职责信息，可从名片库、问答详情栏、推荐卡片或内容关联入口进入。

页面顶部有返回按钮。主体展示姓名、部门路径、岗位、联系方式、负责领域标签、自画像、他画像和个人发布内容。

自画像由本人维护，用于说明自己负责什么、擅长什么、能处理哪些问题。他画像由他人添加的协作事项形成，用于补充实际处理过的事项和擅长场景。

他画像汇总全部有效记录，按事项名称去重。每个事项统计不同评价人的数量和最近添加日期，优先展示评价人数更多的事项，数量相同时展示较新的事项。汇总结果采用自适应气泡图展示：评价人数越多，气泡越大；气泡使用多色循环，并通过确定性避碰布局避免重叠。没有有效事项时展示空状态。人员主页中他画像区域与自画像区域等高，最小高度为 350 像素。

个人发布内容区域展示该人员发布的流程说明、常见问题、经验文章等内容。内容卡片可点击进入内容详情页。

九、内容发布

内容发布用于新增或编辑平台内容。

页面顶部展示返回按钮和标题”内容发布”。表单字段包括标题、关联领域、发布人、内容摘要、正文。标题、摘要和正文为必填项；关联领域用于后续人员推荐依据沉淀。不设内容类型字段。

新增内容时，发布人默认为当前登录用户，且不可修改为他人。后续如需支持代发布场景，必须由管理员授权并在权限规则中单独说明。提交后内容同步到个人中心和人员主页，并作为推荐合适的人时的辅助依据。

编辑内容时，表单带入已有内容。编辑状态下显示“删除内容”按钮。提交后更新原内容；删除后移除内容，并刷新相关列表和统计。

内容发布成功后不应跳到无关页面。系统应给出明确保存状态，并允许用户继续查看或返回来源页面。

十、内容详情与发布内容查看

平台不提供独立的内容检索页面，也不在 Agent 页面提供查内容入口。内容详情只从个人中心“我的发布”、人员主页的个人发布内容等明确来源进入。

内容列表卡片仅在“我的发布”和人员主页等场景展示。卡片包含标题、发布人、发布日期、标签、摘要和置顶标记。点击卡片进入内容详情页。

内容详情页展示标题、发布人、发布日期、标签、摘要和正文。本人内容可以展示置顶按钮；非本人内容只允许查看。内容详情页暂不展示反馈按钮，不直接提供编辑和删除入口，编辑和删除必须通过个人中心”我的发布”列表中的对应按钮操作。

十一、后台管理

后台管理用于展示平台运营情况，不做复杂审批后台。页面顶部只展示标题“后台管理”，不需要返回按钮。

顶部指标区横向展示四张指标卡：参与人员数量、发布内容数量、覆盖领域数、本周推荐量。指标应来自真实业务数据或系统统计口径。

主体区左右两列。左侧是“本周推荐热度排行”，默认展示被推荐次数最高的前 10 位人员。每条排行包含序号、姓名、部门、岗位和推荐次数。

右侧是“周日活数”趋势图，展示一周内每日活跃数。顶部提供“本周 / 上周”切换。默认展示本周，点击左箭头切换上周；切到上周后，只展示返回本周的右箭头。不要扩展成复杂日期选择器。

后台页面应保持紧凑，重点服务运营观察：有多少人参与、发布了多少内容、哪些领域覆盖、哪些人被高频推荐、最近活跃情况如何。

十二、权限规则

普通用户可以提问、查看人员名片、查看人员主页、查看人员主页中的发布内容、维护自己的个人主页、发布自己的内容、编辑和删除自己的内容、为他人补充画像。

普通用户不能编辑他人个人主页，不能编辑或删除他人发布内容，不能置顶他人内容，不能伪造他人评价。

内容操作必须以当前登录用户身份判断权限。按钮隐藏只是界面层，后端接口也必须校验权限。

后台管理可根据角色开放。普通用户如无管理权限，可以不展示后台入口，或进入后只展示允许查看的统计。管理员可查看全局统计、推荐排行和活跃趋势。

十三、业务对象

人员对象应包含用户标识、姓名、部门路径、岗位、联系方式、负责领域、自画像、他画像、推荐次数、内容数量、更新时间等信息。部门路径应支持一级部门、二级部门、三级部门，用于名片库筛选和人员主页展示。

内容对象应包含内容标识、标题、发布人、关联领域、标签、摘要、正文、发布日期、更新时间、置顶状态、浏览次数、被推荐次数、可见状态等信息。不设内容类型字段。

会话对象应包含会话标识、用户标识、标题、创建时间、更新时间、对话轮次、问题内容、回答内容、推荐人员和待确认动作。

评价对象应包含评价标识、评价人、被评价人、评价日期和事项标签（`tag`）。事项标签是当前评价的主数据字段；为兼容历史或 Agent 草稿数据，读取和匹配时可回退使用旧的评价文本字段（`text`）。当前实现未包含来源场景和可见状态字段。

反馈对象应包含反馈标识、用户标识、反馈对象类型、反馈对象标识、反馈值、提交时间。反馈对象可以是回答或人员推荐。

十四、智能推荐逻辑

系统接到用户问题后，应先识别问题意图，只支持推荐合适的人、修改个人信息、为他人做评价、发布内容四类 Agent 动作。

系统应抽取问题中的关键词、业务领域、流程名、系统名、部门名和人员名，并用这些信息匹配人员。已发布内容只能作为人员推荐的辅助依据，不直接形成内容检索结果。

人员推荐应综合考虑负责领域、岗位职责、自画像、他画像事项、历史内容、近期推荐情况和组织部门关系。匹配他画像时优先使用事项标签，兼容旧记录时回退使用评价文本。推荐结果不只给姓名，还要给出可解释理由。

当用户问题与资料维护、内容发布、他人评价相关时，系统不应只回答文字，而应生成可确认的操作卡片，让用户可以直接确认或进入手动编辑。

# 首问必答平台 架构设计说明

> 版本：V1.0（评审稿）
> 适用范围：架构评审 / 方案评审 / 技术交底

---

## 1. 系统定位与总体架构

首问必答平台是一个以「找对人、问清事」为核心的企业内部智能问答系统。用户用自然语言提问，系统判断意图后：要么从组织与知识资产中找出最合适的责任人/专家并给出名片，要么检索已沉淀的知识文档给出带引用的回答，要么把用户的写操作意图（维护资料、为他人画像、发布内容）转化为可确认的草稿，由用户确认后落入业务系统。

系统采用前后端分离、业务与智能解耦的四层结构：

1. **交互层**：Web 前端，提供智能问答、名片库、个人中心、后台管理、Agent 可观测五个界面。
2. **业务服务层**：统一业务后端，负责账号权限、人员与部门、内容与审核、评价、会话等确定性业务数据的读写与规则校验，是业务事实的唯一写入方。
3. **智能服务层（Agent）**：独立的智能问答服务，承担意图识别、问题理解、概念链接、多路检索、排序与回答生成，**不直接写业务数据**。
4. **数据与知识资产层**：PostgreSQL（业务数据 + 标签概念体系 + 向量索引）、OKF 知识仓库（Git 受控的 Markdown 文档库）。

关键架构原则：**业务写入只发生在业务服务层；智能层只读、只推理、只产草稿；一切知识访问经过知识服务接口（MCP）；正式责任数据与自填数据严格区分权重。**

## 2. 核心数据架构：标签三层模型

名片标签是自由文本，用户问句是另一种说法，两者之间需要一个中枢来做语义对齐。为此设计了三层标签体系：

```
用户问句  ──►  中间概念层（标准概念 + 别名）  ──►  原始标签层（员工自由填写）
                                                      │
人员  ◄──  人员-标签关系（含信任分档）  ◄──────────────┘
```

- **原始标签层（RawTag）**：员工/同事填写的标签原文，原样保存、永不改写，保证事实可追溯。
- **中间概念层（Concept）**：企业级的标准概念（如「智能体平台」「大数据平台」），外加登记的**标准别名**（如 llm、hadoop）。原始标签通过「标签-概念映射」挂接到概念上；同一个概念可以汇聚多种写法（agentos / 高码平台 / agent平台 → 智能体平台）。
- **人员-标签关系层**：记录"谁的什么标签、来源是什么"。来源分三类：本人自填、管理员维护、同事评价。

**概念的来源与归并**：新标签进入系统时，走「召回 → 判定」的概念链接流程——先精确匹配现有概念/别名/历史映射，再由模型在候选集合内做受约束判定：挂接到已有概念，或建议建立一个规范命名的新概念。由此避免"一个写法一个概念"的碎片化，保证概念层长期收敛、干净。

**信任分级（防乱贴标签）**：同事给他人打的标签默认处于「待放行」状态：本人会收到通知并决定是否放行。已放行的标签与本人自填标签**同权**；未放行的标签在检索时**降权**（仍可命中但排名靠后），从机制上避免"被乱加标签后被频繁误推"的骚扰。

## 3. 智能问答主链路

一轮问答在智能服务层内按以下阶段流水线执行，每个阶段独立超时、可降级、全程留痕。

### 3.1 接入与上下文

请求携带用户身份，系统校验并构建可信的用户上下文（身份、部门、权限级别）；同时加载该会话的近期对话历史，用于追问和指代的理解。

### 3.2 意图识别

由大模型把问题分类为五类之一：**找人、查知识、编辑修改、闲聊、无法识别**。对"谁负责X""查电话"这类百分百确定的模式，用确定性规则直接分流以节省模型延迟；模型不可用时降级到规则路由并显式标记降级。找人类问题进一步细分查询类型：查联系方式、明确责任查询、故障诊断找人、专家发现。

### 3.3 问题结构化

把问题拆解成结构化要素：涉及的系统/领域/事项、对象、症状、职责线索，以及显式提到的人名和部门。拆解采用「词典显式匹配 + 模型抽取」双通道：凡是在词典（人名、部门、概念名、别名）中显式出现的，标注为"显式"；模型推断的标注为"推断"，两者在后续环节区别对待。追问中省略的主语（如"他的电话呢"）会从对话历史中补全。

### 3.4 概念链接

把拆解出的词项逐一与中间概念层对齐，召回分六级，按确定性从高到低：

1. 概念标准名精确匹配
2. 已登记别名精确匹配
3. 前缀/包含匹配（解决"用户问反欺诈、标签叫反欺诈算法"的长短错位）
4. 历史标签映射复用
5. 文本模糊相似（只产候选）
6. 概念向量相似（只产候选）

**只有前四级确定性命中才会被自动确认**；后两级只产出候选，进入消歧流程，绝不靠模糊猜测直接定论。问句无法对齐任何概念时，检索直接给出"未找到"而非强行推荐。

### 3.5 多路检索

按查询类型选择检索路径：

- **查联系方式**：单路，人员名录精确匹配（不走概念与语义，保证确定性）。
- **明确责任查询**：结构化检索（概念 → 标签 → 人员证据）+ 正式责任查询（经知识服务接口，命中正式责任登记时给出责任部门、时限、升级路径；语义兜底带词元重叠校验，防止"堡垒机"被误关联到无关责任）。
- **故障诊断 / 专家发现**：**双路混合召回**——结构化路径（标签证据）与知识检索路径（全文/向量混合检索自我介绍与发布内容）并联，命中的文档再折算为人员证据。

知识检索采用「全文检索 + 向量检索」双通道加 RRF 融合排序，并做权限预过滤与二次校验。

### 3.6 排序

候选人员合并后进入确定性排序。排序依据证据的语义权重，策略随查询类型而变，但全局优先级固定：

| 优先级 | 证据类型 | 说明 |
|---|---|---|
| 最高 | 正式责任登记 | 有正式责任记录者排最前（含责任部门/时限/升级路径） |
| 高 | 本人自填负责领域 | 精确命中的自填标签 |
| 高 | 已放行的他人标签 | 与自填同权 |
| 中 | 自画像/文章推断 | 自我介绍、发布内容中的语义证据 |
| 低 | 未放行的他人标签 | 权重减半——存在但不优先 |
| 辅助 | 历史反馈回流 | 用户"有帮助/没帮助"的反馈只做小幅微调，不产生或消除候选 |

排序是确定性的、可解释的：每个人的得分由哪几类证据、各自多少分构成，全部落库可查。

### 3.7 置信门禁与回答生成

排序结果经过置信门禁：可信则正常回答；证据不足则诚实空答或反问澄清，**不允许编造责任人**。回答正文给出命中依据与建议，并附最多五张人员名片（姓名、部门、职位、上级、联系方式、负责领域标签、自我介绍），点击名片直达人员主页。

### 3.8 知识问答分支

知识类问题经知识服务接口检索已发布文档：有证据时给出"事实 + 引用来源"，无证据时诚实说明未找到，并建议换说法或补充关键词。

## 4. 写操作链路（人机确认闭环）

用户的写操作意图（改资料、为他人画像、发内容）不直接执行，而是走确认闭环：

1. 意图识别为"编辑修改"后，先按确定性规则快速判断写操作类型；规则未覆盖的长尾说法由模型做受约束分类。
2. 系统按提问的明确程度**预填草稿卡片**：能提取多少填多少，不编造缺失字段。
3. 用户点击卡片，右侧展开详情侧边栏，可**直接修改**草稿内容；也可一键跳转对应业务页面（个人中心/画像页/发布页）继续编辑。
4. 用户点「确认」后，**由前端调用业务服务层的正式接口**完成写入。智能层自始至终不触碰业务表。
5. 写入完成后，业务服务层同步刷新标签概念体系，并发出变更事件，驱动知识资产与检索索引的增量更新（见第 5 节）。

---

## 5. 数据新鲜度链路（变更 → 知识 → 索引）

为保证"新发布的内容、新更新的画像"可被检索到，设计了事件驱动的增量链路：

```
业务变更（内容发布/修改/删除、人员资料或画像变更）
   │  业务服务层写入 publish_events 事件表(同事务,随业务提交)
   ▼
智能层事件消费者(轮询)
   │  按事件类型增量重建对应的 OKF 文档(Git 受控仓库,每次发布一个版本)
   ▼
RAG 索引器按「文档 ID + 版本 + 内容哈希」幂等增量更新向量索引
   │  全量重建时:新版本 → 冒烟验证 → 原子切换指针(旧版本可随时回滚)
   ▼
检索立即可见(标签类变更经实时 SQL 视图天然即时生效,无需重建索引)
```

OKF 知识仓库对文档有字段白名单与发布校验链：人员动态标签、联系方式等敏感或易变数据不写入对外档案；只有校验通过的版本才可被索引消费。

## 6. 可靠性与安全设计

- **分层降级**：意图模型失败 → 规则路由；要素抽取失败 → 保留词典匹配；向量模型失败 → 关键词单路检索；知识服务失败 → 结构化路径照常，并显式标记降级来源。任何单点故障都有明确的退化路径，且降级状态对用户可见、对管理员可查。
- **权限与可见性**：业务接口全部 JWT 鉴权；管理类操作（成员/部门/审核/置顶/可观测）仅管理员；检索按用户敏感级别做预过滤与二次校验；登录账号停用后立即无法登录。
- **身份可信**：智能层的用户上下文由服务端从令牌/名录构建，前端自报的角色不作数。
- **防滥用**：他人标签需本人放行方获全权重（见第 2 节）；反馈点踩需选原因，反哺排序优化与运营分析。
- **缓存策略**：概念词典与查询-概念结果短缓存（30 秒），保证新标签快速可见的同时避免高频全表扫描；意图规则短路与模型连接复用降低平均时延。

## 7. 可观测性设计

每一轮问答全链路留痕并持久化：运行轨迹（问句、用户、总耗时、是否降级）、各处理节点的耗时/状态/输入输出摘要、概念链接轨迹（词项→候选→确认）、知识服务调用日志、推荐候选及排序证据、知识检索命中记录、用户反馈（含点踩原因，与推荐运行记录关联）。

管理员在「Agent 可观测」界面可按时间/用户/问题检索任意一轮问答，逐节点展开查看：意图判定结果、概念对齐过程、走了哪条检索路、每个候选人的证据构成与得分、最终回答与卡片、用户反馈。该能力同时支撑准确率评测、问题回溯与推荐策略的持续优化。

后台管理另提供「推荐反馈」可视化：反馈总量、有帮助率、七日趋势、点踩原因分布、逐条明细（问题 + 推荐人选 + 结果 + 原因），用于运营评估与后续调优。

## 8. 部署形态

- 前端静态资源经 Nginx 托管，同端口反向代理业务接口与问答事件流（SSE 长连接透传）。
- 业务服务与智能服务以独立进程常驻（systemd 托管，异常自启）。
- PostgreSQL 单实例承载业务、标签概念与向量索引三类数据（分 schema 隔离）。
- 部署与其他应用完全隔离：独立目录、独立端口、独立数据库、独立进程与站点配置。

## 附：关键设计决策摘要

| 决策点 | 选择 | 理由 |
|---|---|---|
| 智能层写业务表 | 禁止，只产草稿 | 写操作必须经业务层校验与确认，保证数据可信 |
| 模糊相似直接定论 | 禁止，只作候选 | 责任人指认必须确定性可解释 |
| 他人标签直接全权重 | 禁止，需本人放行 | 防乱贴标签导致的推荐骚扰 |
| 找不到时 | 诚实空答/反问澄清 | 不编造责任人 |
| 知识访问 | 统一走知识服务接口 | 权限、审计、降级集中治理 |
| 索引更新 | 事件驱动增量 + 原子切换 | 数据新鲜且可回滚 |

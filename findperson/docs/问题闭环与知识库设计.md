# 问题闭环 · 知识沉淀 · 反馈回流 设计稿

> 目标:让"问一个人"变成"问一次就被沉淀下来"。五个部分其实是一条链:
> **收邮件(可选)** → **问题跟踪(个人中心"我的问题")** → **沉淀成 FAQ** → **知识库(人看 + Agent 用)** → **反馈回流自主优化**。

---

## 一、问题跟踪:个人中心新增"我的问题"

### 数据表 `public.issues`

| 字段 | 说明 |
|---|---|
| id | 主键 |
| user_id | 提问人 |
| session_id / message_id | 来源会话与消息(指向 agent 侧问答记录) |
| question | 原始问题文本 |
| summary | LLM 归一化后的一句话问题 |
| status | `not_contacted` 未联系 / `processing` 处理中 / `resolved` 已解决 / `unresolved` 未解决 |
| assignee_person_id | 责任人(取该轮推荐的第一人,可改) |
| last_action_at | 最近一次动作时间(发邮件/改状态/写备注) |
| resolved_at | 解决时间 |
| resolution_note | 结果备注 |
| repeated_count | 同一问题被重复提问的次数(用于沉淀打分) |
| source | `sync` 从对话同步 / `manual` 手动新建 / `mail` 邮件触发 |
| created_at / updated_at | — |

配套时间线表 `public.issue_events`:`issue_id / event_type(created·status_changed·mail_sent·mail_received·note) / detail / operator_id / created_at`。个人中心每条问题展开就是这条时间线。

### 同步机制(重点:先筛选,再入库)

从对话同步**不是无脑全量搬**。同步时对每条助手回答跑一次 LLM 判定:

```
输入:用户问题 + 助手回答 + 该轮推荐的候选人
输出(JSON):
  is_valid        是否是需要有人负责落实的业务问题(闲聊/寒暄/纯功能询问 → false)
  summary         归一化问题(去掉口语与错别字,保留业务要素)
  duplicate_of    与已有条目是否是同一个问题(给候选 id 或 null)
  assignee_id     建议责任人(从该轮推荐里取)
```

规则:
- `is_valid=false` 不入库;
- `duplicate_of` 命中已有条目 → 不新建,该条目 `repeated_count + 1`(这就是"问得多"的天然累积);
- 其余入 `issues`,状态默认"未联系"。

同步入口:**个人中心"我的问题"里的"从对话同步"按钮**(也可加每日自动跑一次,见待确认事项)。

### 页面(个人中心新栏目)

- 顶部分段筛选:`未联系 / 处理中 / 已解决 / 未解决`,右上角统计"我发起 N 条,已解决 M 条,解决率 X%"。
- 每行:问题摘要 · 责任人 · 状态徽标 · 最近动作时间;操作:改状态(一键) / **发邮件**(复用现有邮件弹窗) / 写备注 / 展开时间线。
- 邮件联动:`/mail/send` 成功后,若收件人对应某条问题的责任人 → 该问题自动置**"处理中"**,时间线记一条"已发邮件给 X"。

### 管理端

提问总数、解决率、平均解决时长、按部门/责任人的问题量与解决率(挂现有管理看板)。

## 二、问题沉淀成知识(FAQ)

### 沉淀打分(自动挑候选)

每条问答按下表累计"沉淀分",达到阈值进候选池:

| 信号 | 分值 |
|---|---|
| 提问人被标记"已解决" | +5 |
| 同一问题被重复提问(repeated_count) | 每次 +2 |
| 回答被点赞 | +2 |
| 被点踩 | -3 |
| 命中知识缺口榜单(见第四部分) | +1 |

### 候选池 `public.knowledge_candidates`

`id / question / answer / summary / score / signals(jsonb) / status(pending·approved·rejected·merged) / source_issue_ids / target_faq_id / reviewed_by / reviewed_at / created_at`

### 人工确认(管理端"知识候选"页)

三个动作:
1. **转成 FAQ** → 写 `public.faqs`(见下),责任人沿用 issue 的 assignee;
2. **转成文章草稿** → 生成 `contents` 草稿,走现有"发布→审核"链路,作者=被推荐的责任人;
3. **忽略 / 合并到已有 FAQ**。

### FAQ 表 `public.faqs`

`id / question / answer / tags / owner_person_id(责任人) / scope_department_ids(可见范围) / source(issue 或 candidate) / version / status(draft·published·archived) / published_at / updated_at`

### 问答时优先命中 FAQ

问答链路加一步"FAQ 先行":问题进来先做 FAQ 检索(向量 + 关键词,命中阈值可调)
- 命中 → 直接返回标准答案 + 责任人 + "来自知识库"标记,**不再走推荐人流程**(或仅作为补充展示);
- 未命中 → 走现有 RAG + 推荐人流程,并把"未命中"记入知识缺口(第四部分)。

## 三、专门的知识库:一份源,两个视图

### 核心原则

**OKF 目录是唯一事实源**,人和 Agent 看的是同一份东西的两个视图——避免"人维护一份、机器吃另一份"导致不一致。

```
业务表(faqs / contents / people / departments / responsibilities)
      │  发布事件(publish_events)
      ▼
knowledge-okf/  ← 唯一事实源(markdown + frontmatter,可 git 追溯)
      ├── 面向 Agent:RAG 切片索引(现有链路,直接复用)
      └── 面向人:知识库页面(按类型/标签/部门浏览、搜索、看责任人、提纠错)
```

### 目录与模板(OKF 现有 8 类,已在用 4 类)

| 目录 | 用途 | 模板必备字段(frontmatter) |
|---|---|---|
| `faqs/` | **新增**。模板化问答 | question / answer / owner / scope / tags / source_issue / updated_at |
| `processes/` | **新增**。办事流程 | scenario / prerequisites / steps / contact / pitfalls |
| `contents/` | 已有。文章 | (现状) |
| `people/` | 已有。人员画像 | (现状,不含标签,合规红线) |
| `departments/` | 已有。部门 | (现状) |
| `responsibilities/` | 已有。责任事项 | (现状) |
| `policies/` | 预留。制度 | title / scope / effective_date / owner |
| `relationships/` | 预留。人-系统/人-人关系 | from / to / relation |

模板 = frontmatter 的 schema,入库时做校验(缺必备字段不允许发布)。

### 面向人的知识库页面

- 列表/搜索:按类型筛(FAQ / 流程 / 文章 / 责任 / 制度),按标签或部门筛;
- 每条显示:标题、摘要、责任人、更新时间、"来源:某次工单/某个问题";
- 详情页底部两个按钮:**"这个答案有用/没用"** 和 **"我要纠错/补充"**(纠错直接进第四部分的复核队列);
- 权限:沿用知识条目的"可见范围"(OKF 文档已有 visibility / allowed_departments / sensitivity 字段,直接复用)。

## 四、反馈回流与自主优化(四层,从轻到重)

```
提问 → 回答 → 反馈(赞/踩/解决状态) → 信号分流 → 知识库/排序更新 → 再索引 → 下次答得更好
```

| 层 | 信号 | 自动动作 | 人工动作 |
|---|---|---|---|
| 1. 排序微调(**已有**) | 点赞/点踩 | 推荐人得分 ±权重,自动生效 | — |
| 2. 回答纠错 | 点踩 + 原因 | 自动建"待改任务",挂在对应 FAQ/候选项上 | 责任人/管理员复核 |
| 3. 知识更新 | 标记"已解决" | 该问答自动进沉淀候选(高置信) | 一键确认成 FAQ |
| 3'. 知识缺口 | 问答未命中 FAQ / 没找到责任人 | 按问题聚类,生成"该补什么"榜单(次数×人数排序) | 认领并沉淀 |
| 3''. 责任移交 | 责任人离职/调动 | 其名下 FAQ 自动标"待移交"并通知管理员 | 指定新责任人 |
| 4. 评测防退化 | 黄金问题集(从已解决问答中抽) | 每周自动跑一遍,命中率/一致性下降则告警 | 排查原因 |

**边界**(建议):自动只做到"排队/提议/告警",**改知识内容一律人工确认**;唯一自动生效的是第 1 层的排序权重。等沉淀链路跑稳后,再考虑让 LLM 直接改 FAQ 草稿(仍需人审)。

## 五、收邮件(现在能发,能不能收?)

**能收,但现在的代码没有,需要新做。** 事实:源仓库只有 SMTP 发信,没有 IMAP 收信。

- 163 邮箱支持 IMAP:`imap.163.com:993`(SSL)。需要在 163 后台**开启 IMAP 服务**并拿到授权码(和 SMTP 那个可能不是同一个码)。
- 推荐做法:**定时轮询**(每 1–5 分钟拉一次新邮件),不做长连接。理由:实现简单、断线自愈、163 对长连接有限制。
- 落库 `public.mail_messages`:`direction(in/out) / from_addr / to_addr / subject / body_text / thread_key / matched_issue_id / received_at`。
- 与问题跟踪打通:按 `In-Reply-To` 或主题里的标识匹配到 `issues`,收到回信 → 时间线记一条"收到 X 的回复",并提示用户"是否已解决?"。
- 展示:挂在"我的问题"的时间线里(发出去的 + 收回来的),不单独做邮件客户端。
- 注意:先不做附件;163 对 IMAP 有频率限制,轮询间隔别低于 1 分钟。

**需要你提供**:163 后台开启 IMAP 后的授权码(以及确认是否允许收全部邮件,还是只收"回复类")。

## 六、实施顺序建议

| 阶段 | 内容 | 预估 |
|---|---|---|
| 1 | 问题跟踪:表 + 同步接口(LLM 筛选) + 个人中心"我的问题"栏目 + 邮件联动置"处理中" + 管理端解决率 | 1–2 天 |
| 2 | 沉淀池 + 管理端确认页 + FAQ 表 + OKF faq 模板与索引 + 问答"FAQ 先行" | 2–3 天 |
| 3 | 面向人的知识库页面 + 流程模板 + 纠错/缺口/黄金问题集 | 2–3 天 |
| 4 | 收邮件(IMAP 轮询 + 时间线) | 1 天(需先拿到 IMAP 授权码) |

## 七、待确认的决策点

1. **同步方式**:只做"手动点同步",还是再加"每天自动跑一次"?(建议:先手动,后加自动)
2. **FAQ 审批人**:管理员一级,还是"责任人 + 管理员"两级?(建议:两级,责任人先看)
3. **知识可见范围**:默认全公司可见,还是按部门?(涉及敏感问答,建议默认按部门 + 管理员可放宽)
4. **收邮件范围**:只收与已有问题相关的回信,还是全收?
5. **自动化的度**:是否同意"自动只排队、改内容人工确认"这个边界?
6. **"问得多"的统计口径**:按不同提问人计数(防同一人反复问刷分),是否认可?(建议:认可)

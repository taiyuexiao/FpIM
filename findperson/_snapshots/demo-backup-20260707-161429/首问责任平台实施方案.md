# 首问责任平台实施方案

一、实施目标与建设口径

本实施方案基于《首问责任平台方案v2》编写，目标是把当前静态 Demo 扩展为一套可开发、可演示、可联调、可逐步上线的首问责任平台。

建设目标：平台以“首问助手”为统一入口，让用户通过自然语言完成找负责人、查询人员、查询内容、发布内容、修改个人信息、评价他人等操作；同时把人员画像、发布内容、提问记录、推荐结果和反馈数据统一入库，形成可持续运营的首问责任数据资产。

建设口径：第一阶段不追求一次性建设成复杂工单系统，也不依赖一开始就有完整规则表。优先围绕“内容检索 + 人员关联 + 推荐解释 + 反馈沉淀”完成可运行闭环，再逐步增强标签体系、向量检索、运营分析和权限治理。

当前基础：项目已有静态 Demo，覆盖首问助手、名片库、人员主页、我的主页、内容发布、他画像评价和后台管理；`assets/app.js` 中已有本地匹配函数、模拟人员数据、模拟内容数据和本地存储逻辑。后续实施应复用现有页面与交互，不推翻重做。

二、总体实施范围

本期建议分为六个功能域实施。

首问助手：作为首页统一入口，负责接收自然语言输入、识别用户意图、调用对应服务，并返回推荐人、相关内容、操作确认或跳转入口。

人员与职责画像：建设人员基础信息、负责领域、自画像、他画像、联系方式、部门科室、岗位职级等数据维护能力，并支持在名片库和个人主页展示。

内容发布与检索：支持用户发布流程说明、常见问题、经验文章等内容，内容进入审核流程，审核通过后参与问答检索和人员推荐。

智能匹配推荐：对用户问题进行意图识别、关键词抽取、语义检索、人员聚合评分和推荐理由生成，输出可解释的首问推荐结果。

后台管理：支持管理员维护人员、部门、标签、内容审核、推荐记录、提问记录、运营指标和效果反馈。

数据沉淀与运营分析：记录用户提问、系统推荐、用户采纳、反馈评价、内容命中情况，为后续优化推荐效果提供依据。

三、推荐技术架构

整体架构采用“前端页面 + 后端服务 + 业务数据库 + 向量检索 + 大模型能力”的分层方式。

前端层：复用当前 `index.html`、`assets/styles.css`、`assets/app.js` 的页面结构和交互原型，逐步把本地模拟数据替换为接口数据。若后续需要工程化，可迁移到 Vue 或 React，但第一阶段不建议因框架迁移影响业务验证。

后端服务层：建议使用 FastAPI 建设接口服务，负责用户、人员、内容、评价、推荐、后台统计等业务接口。FastAPI 对 Python 向量检索、文本处理和大模型调用更友好，适合本项目后续智能匹配扩展。

数据库层：建议使用 PostgreSQL 存储结构化业务数据；如需要向量检索，可启用 pgvector 插件，把人员画像文本和内容文本生成向量后存入数据库。若部署条件暂时不支持 pgvector，可先用普通 PostgreSQL + 本地关键词匹配完成 Demo 闭环。

智能能力层：第一阶段可采用规则意图识别 + 关键词匹配；第二阶段接入 Embedding 模型做语义检索；第三阶段接入大模型做意图判断、发布内容整理、推荐理由润色和对话式引导。

文件存储层：本期内容以文本为主，可直接入库；如后续支持附件、制度文件、流程图，可增加对象存储或本地文件存储，并在内容表中保存文件地址。

四、核心业务流程

首问找人流程：用户在首页输入问题，系统先识别意图为“找负责人”，然后抽取关键词和领域词，再检索相关内容和人员画像。系统把命中的内容按发布人、标签、摘要和正文聚合到人员维度，结合人员负责领域、自画像、他画像计算综合分，最终输出推荐人、推荐理由、联系方式和相关内容。

内容发布流程：用户通过首问助手或内容发布页发起发布。系统引导补充标题、类型、正文、标签、适用范围和发布人，用户确认后写入内容表，默认进入“待审核”状态。管理员审核通过后，内容状态变为“已发布”，参与后续检索和推荐。

个人信息维护流程：用户通过“我的主页”或首问助手提出修改需求。系统识别字段，例如联系方式、负责领域、自画像，生成修改预览，用户确认后写入人员画像数据，并同步到我的主页、个人主页和名片库。

他画像评价流程：用户选择被评价人并填写评价内容，也可以通过首问助手发起“我要评价某人”。系统保存评价记录，经必要审核后展示到个人主页，并作为推荐匹配的辅助依据。

查询人员流程：用户输入“某部门有哪些人负责大模型”或在名片库搜索筛选。系统按关键词、部门、负责领域、自画像和他画像匹配人员，并返回人员列表。

查询内容流程：用户输入“有没有 Key 申请流程”。系统检索已发布内容，返回标题、摘要、发布人、标签和详情入口；如果内容关联到某个人，也可提示该内容发布人是否适合作为首问对象。

五、数据模型设计

人员表 `users`：保存平台人员基础信息。核心字段包括 `id`、`name`、`department_id`、`role_title`、`contact`、`account_status`、`created_at`、`updated_at`。

部门表 `departments`：保存部门科室结构。核心字段包括 `id`、`name`、`parent_id`、`sort_order`、`status`。

人员画像表 `person_profiles`：保存职责画像信息。核心字段包括 `id`、`user_id`、`domains`、`self_portrait`、`service_scope`、`completeness_score`、`updated_by`、`updated_at`。

他画像评价表 `peer_reviews`：保存同事或协作方对人员的补充评价。核心字段包括 `id`、`person_id`、`reviewer_id`、`review_text`、`status`、`created_at`、`audited_by`、`audited_at`。

内容表 `contents`：保存流程说明、常见问题和经验内容。核心字段包括 `id`、`title`、`content_type`、`summary`、`body`、`owner_id`、`status`、`created_at`、`updated_at`。

标签表 `tags`：保存业务标签、领域标签、部门标签和内容标签。核心字段包括 `id`、`name`、`tag_type`、`status`。

内容标签关系表 `content_tags`：保存内容和标签的多对多关系。核心字段包括 `content_id`、`tag_id`。

人员标签关系表 `person_tags`：保存人员和标签的多对多关系。核心字段包括 `person_id`、`tag_id`、`source_type`。

提问记录表 `question_logs`：保存用户问题和系统分析结果。核心字段包括 `id`、`question_text`、`asker_id`、`intent`、`keywords`、`created_at`。

推荐记录表 `recommendation_logs`：保存每次推荐结果。核心字段包括 `id`、`question_id`、`person_id`、`rank_no`、`score`、`reason`、`matched_content_ids`、`created_at`。

反馈记录表 `feedback_logs`：保存用户对推荐结果的反馈。核心字段包括 `id`、`question_id`、`person_id`、`feedback_type`、`feedback_text`、`created_at`。

向量索引表 `embedding_items`：保存可检索文本的向量。核心字段包括 `id`、`item_type`、`item_id`、`owner_id`、`text_for_embedding`、`embedding`、`updated_at`。`item_type` 可取 `person_profile`、`content`、`peer_review`。

六、接口设计

首问助手接口 `POST /api/assistant/message`：输入用户自然语言和当前用户 ID，输出意图、操作类型、推荐结果、相关内容或待确认操作。该接口是首页的主入口。

匹配推荐接口 `POST /api/match/question`：输入问题文本、部门筛选条件和用户 ID，输出 Top N 推荐人员、推荐理由、相关内容、匹配分数和命中依据。

人员列表接口 `GET /api/people`：支持按关键词、部门、标签查询人员列表，用于职责名片库。

人员详情接口 `GET /api/people/{id}`：返回人员基础信息、职责画像、他画像、发布内容和推荐相关信息，用于个人主页。

我的主页更新接口 `PUT /api/me/profile`：支持当前用户维护联系方式、负责领域、自画像等字段。

内容发布接口 `POST /api/contents`：支持创建流程说明、常见问题和经验文章，默认进入待审核状态。

内容列表接口 `GET /api/contents`：支持按关键词、标签、状态、发布人查询内容。

内容审核接口 `PUT /api/admin/contents/{id}/audit`：支持管理员审核通过或驳回内容。

他画像接口 `POST /api/peer-reviews`：支持提交他画像评价，按配置决定是否需要审核后展示。

后台统计接口 `GET /api/admin/metrics`：返回参与人员数量、发布内容数量、本周咨询热度、日活数据、推荐采纳率等指标。

推荐反馈接口 `POST /api/recommendations/feedback`：记录用户是否采纳推荐、是否有帮助、是否需要继续转问。

七、智能匹配逻辑

第一步，意图识别。系统判断用户输入属于找负责人、发布内容、修改个人信息、查询人员、查询内容、进入人工操作或评价他人。Demo 阶段可以先用关键词规则识别，后续再接入大模型。

第二步，问题解析。对用户问题抽取关键词、领域词、部门词和动作词。例如“大模型 Key 申请找谁”可抽取出“大模型”“Key 申请”“权限流程”等关键词。

第三步，内容召回。系统优先检索已发布内容，因为内容往往能直接说明“谁发布过相关流程、谁沉淀过相关经验”。召回对象包括内容标题、摘要、正文、标签和发布人。

第四步，人员召回。系统检索人员负责领域、自画像、他画像、服务范围、历史推荐反馈等信息，找到可能相关的人员。

第五步，人员聚合评分。把内容召回结果按发布人聚合，再叠加人员画像命中情况。建议初始评分规则如下：

- 负责领域命中：每命中一个领域词加 30 分。
- 自画像命中：命中关键词加 20 分。
- 已发布内容命中：每条相关内容加 25 分。
- 他画像命中：命中关键词加 10 分。
- 部门筛选命中：符合指定部门加 10 分。
- 反馈采纳加权：历史推荐被采纳次数越多，适当加分。

第六步，推荐解释生成。推荐理由必须说明“为什么推荐这个人”，不能只返回姓名。推荐理由应包含命中的负责领域、相关内容、画像依据或历史反馈。

第七步，反馈沉淀。用户点击联系、查看主页、采纳推荐或给出无效反馈后，系统写入反馈记录，用于后续优化排序。

八、开发任务拆分

第一组，后端基础工程。搭建 FastAPI 项目、数据库连接、配置管理、日志、异常处理、接口文档和本地启动脚本。完成后应能启动服务并访问 `/docs`。

第二组，数据库与数据初始化。创建部门、人员、画像、内容、标签、提问记录、推荐记录、反馈记录等表；把当前 `assets/app.js` 中的模拟人员和模拟内容整理成初始化脚本，导入数据库。

第三组，前端接口替换。保留现有页面和交互，把名片库、人员主页、我的主页、内容列表、后台指标从本地数组和 `localStorage` 逐步替换为后端接口。

第四组，首问助手意图路由。实现 `POST /api/assistant/message`，先支持找负责人、发布内容、修改个人信息、查询人员、查询内容、评价他人六类意图；每类意图返回统一结构，便于前端展示。

第五组，匹配推荐引擎。实现问题解析、关键词检索、人员评分、内容关联、推荐理由生成和推荐记录入库。第一版可用规则和关键词完成，第二版接入向量检索。

第六组，内容发布与审核。实现内容创建、编辑、列表、详情、审核通过、驳回和状态展示；审核通过后的内容参与推荐匹配。

第七组，个人主页与他画像。实现我的主页编辑、他画像提交、他画像展示、评价审核和画像完整度计算。

第八组，后台管理与运营看板。实现人员数量、内容数量、热门咨询、推荐采纳率、内容审核队列、标签治理入口和基础运营指标。

第九组，权限与审计。实现普通用户和管理员角色区分；普通用户只能维护本人信息和发布内容，管理员可审核内容、维护部门标签、查看运营记录。关键修改需要记录操作日志。

第十组，测试与验收。围绕首问找人、内容发布、个人信息修改、他画像评价、名片库查询、后台审核等流程编写测试用例，完成接口测试和演示脚本。

九、里程碑计划

第一阶段：Demo 数据后端化，建议 1 周。完成后端项目、数据库表、初始化数据导入、人员列表、人员详情、内容列表、我的主页保存等接口。验收标准是页面不再完全依赖静态数组，核心数据可从数据库读取和更新。

第二阶段：首问助手闭环，建议 1 周。完成意图识别、问题找人、推荐结果、推荐理由、相关内容、推荐记录入库。验收标准是输入“大模型 Key 申请找谁”能推荐相关人员，并解释命中的领域和内容。

第三阶段：内容发布与评价闭环，建议 1 周。完成自然语言发起发布、手动发布、内容审核、他画像提交、他画像展示。验收标准是新增内容和评价能入库、能展示、能影响后续匹配。

第四阶段：后台运营与权限，建议 1 周。完成管理员指标、内容审核队列、标签维护、人员完整度、推荐记录和反馈记录。验收标准是管理员可以看到平台运行数据，并能处理内容审核。

第五阶段：语义检索增强，建议 1 到 2 周。完成 Embedding 生成、向量索引、内容召回、人员画像召回和混合排序。验收标准是用户使用近义表达时，系统仍能找到正确人员和相关内容。

第六阶段：联调演示与验收，建议 3 到 5 天。完成演示数据整理、演示脚本、异常场景处理、页面细节修复和验收材料。验收标准是六条核心演示路径均可稳定跑通。

十、核心验收路径

路径一，问题找人。用户输入“我想申请大模型 Key，应该找谁”，系统推荐负责大模型能力接入和 Key 申请流程的人员，展示联系方式、推荐理由和相关内容。

路径二，查询人员。用户进入职责名片库，按部门或关键词搜索“大模型”，能看到相关人员卡片，并进入个人主页查看画像和发布内容。

路径三，发布内容。用户输入“我要发布一篇大模型 Key 申请流程”，系统引导补充标题、正文、标签和适用范围，确认后写入内容库并进入审核队列。

路径四，内容审核。管理员在后台看到待审核内容，审核通过后，该内容出现在内容列表和发布人主页，并参与后续推荐。

路径五，修改个人信息。用户输入“我的负责领域增加智能体应用”，系统生成修改确认，用户确认后更新我的主页、个人主页和名片库。

路径六，评价他人。用户提交“李华熟悉智能体应用落地，响应很快”，系统保存他画像评价，并在个人主页展示，经后续匹配时作为推荐依据之一。

路径七，反馈优化。用户对推荐结果点击“有帮助”或“未解决”，系统记录反馈，后台能看到推荐采纳情况。

十一、验收标准

功能验收：首问助手、名片库、个人主页、我的主页、内容发布、他画像评价、后台管理七个核心模块均可访问、可操作、可保存数据。

数据验收：人员、画像、内容、标签、提问、推荐、反馈等核心数据均入库，不再只存在页面上下文或浏览器本地存储中。

匹配验收：系统能够根据问题推荐 Top 3 人员，并展示至少两类推荐依据，例如负责领域命中、内容命中、自画像命中、他画像命中。

解释验收：推荐结果必须说明“推荐谁、为什么推荐、可以看哪些内容、如何联系”，不能只输出姓名。

运营验收：后台能查看参与人员数量、发布内容数量、待审核内容、本周咨询热度、推荐记录和反馈情况。

权限验收：普通用户不能审核内容和修改他人基础信息；管理员可以处理内容审核、标签维护和运营数据查看。

演示验收：核心演示路径在连续操作时不报错，新增数据刷新后仍可查看，关键状态有明确提示。

十二、风险与处理策略

风险一，早期没有完整规则表，导致推荐依据不足。处理策略是先从人员画像、发布内容和他画像中做内容检索，再通过用户反馈逐步沉淀规则。

风险二，人员自画像填写不完整，影响推荐效果。处理策略是在我的主页加入画像完整度提示，并由后台展示低完整度人员清单。

风险三，内容质量不稳定，影响检索结果。处理策略是内容默认进入审核队列，管理员审核通过后才参与正式推荐。

风险四，大模型接口暂未确定。处理策略是第一阶段使用规则意图识别和关键词匹配保底，同时保留 Analyzer 接口，后续平滑替换为真实模型。

风险五，推荐结果缺少可信度。处理策略是所有推荐必须展示命中依据、相关内容和反馈入口，让用户能判断推荐是否可靠。

风险六，平台被误用为普通问答系统。处理策略是产品定位始终围绕“问题找人和职责协同”，回答重点放在推荐负责人、协助人、相关内容和后续动作上。

十三、第一版开发清单

第一版建议优先完成以下内容：

- 建立 FastAPI 后端工程和 PostgreSQL 数据库。
- 建立人员、部门、画像、内容、标签、提问、推荐、反馈表。
- 将当前 Demo 的 20 名人员和内容数据导入数据库。
- 改造前端人员列表、人员主页、内容列表、我的主页为接口读取。
- 实现首问助手找负责人接口。
- 实现内容发布和审核流程。
- 实现他画像评价提交和展示。
- 实现后台基础指标和审核队列。
- 实现推荐记录和用户反馈记录。
- 准备 6 条验收演示脚本。

十四、建议交付物

本项目建议最终交付以下材料：

- 可运行前端页面。
- 可运行后端服务。
- 数据库建表脚本和初始化数据脚本。
- 接口文档。
- 智能匹配规则说明。
- 演示数据说明。
- 测试用例和验收清单。
- 部署说明。
- 管理员操作说明。
- 用户演示脚本。

十五、结论

首问责任平台的第一版实施重点，不是先建设复杂规则系统，而是先把“用户提问、内容命中、人员推荐、推荐解释、反馈沉淀”跑通。当前 Demo 已经具备可复用的页面和交互基础，下一步应优先把数据从前端模拟迁移到后端数据库，再补齐首问助手接口、匹配推荐逻辑、内容审核和后台运营能力。

按照上述路径实施后，平台可以从静态演示升级为可真实录入、可查询、可推荐、可反馈、可运营的首问责任制支撑系统。
